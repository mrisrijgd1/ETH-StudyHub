1. The story: the golem locks the box

The glued boxes of lesson 9 had a weakness: their lids were open. A careless apprentice could reach into a rational and put a 0 in the bottom box, and the golem, literal as always, would divide by it.

So the scribes lock the lid. Inside, the small boxes are now private: only the box itself can touch them. On the outside, the box gets a row of bell-pulls, each with a label: "tell me your top number", "set your bottom number". Behind each pull is a small helper who lives inside the box. The helper for "set your bottom number" refuses a 0.

And a box can no longer be made empty and filled later: whoever makes one must say at once what goes in, and a helper at the factory door checks it. From then on, every box in the workshop holds a valid number, from the moment it exists to the moment it's thrown away.

In C++: the locked box is a class with private members; the bell-pulls are public member functions; the helper at the factory door is a constructor. The aim (p. 161): the user sees what a type can do, not how it is stored.

2. Header and implementation file (script ch. 13, p. 160)

Like functions in lesson 4, a type with its operators can go into a library: the header file rational.h holds the struct and the declarations of its functions, with their PRE and POST; the implementation file rational.cpp starts with #include "rational.h" and holds the definitions. A user reads only the header: it says what the functions do, not how. Section 7 shows how this works for member functions.

3. Encapsulation (script 13.1)

Three wishes motivate this chapter (p. 161):

  • Invariants must hold. For every rational, d ≠ 0; perhaps we even want every rational stored in lowest terms.
  • The user gets the "what", not the "how". You use v.size(), v[i] and v.push_back(j) without knowing how a vector stores its elements.
  • The representation can change without changing user code. Complex numbers could be stored in polar or in Cartesian coordinates; the user shouldn't notice the switch.

Information hiding principle (p. 161): a type is uniquely defined by its possible values and its functionality. The representation should not be accessible. Not representation but functionality is offered. In C++, this is done with classes.

4. Classes: public and private (script 13.2)

A class is a variant of a struct (p. 161):

class rational {
  int n;
  int d; // INV: d != 0
};

The keywords public: and private: control which members can be used outside the class. Everything after public: is usable everywhere; everything after private: only inside the class. The only difference between struct and class (p. 161–162): in a struct, members are public unless said otherwise; in a class, they are private unless said otherwise. So struct rational { private: int n; int d; }; is the same as class rational { int n; int d; };, and class rational { public: int n; int d; }; is the same as the struct of lesson 9.

Worked example 1: inaccessible members (script Example 13.1, p. 162)

class rational {
  int n;
  int d;
};

rational r;
r.n = 1;      // (1)
r.d = 2;      // (2)
int i = r.n;  // (3)
  1. Which of (1), (2), (3) compile?
    Answer

    None: n and d are private, because a class hides by default. Reading (3) is as forbidden as writing. The compiler says "n is private within this context".

  2. And with struct instead of class?
    Answer

    All three compile: in a struct everything is public by default.

  3. What is the use of hiding something if nobody can use it?
    Answer

    None yet, as the script says ("That is weird"). Section 5 adds the bell-pulls: member functions.

5. Member functions (script 13.3)

Member functions are functions declared inside the class. They have access to the private members, and they can be public (p. 162–163):

class rational {
public:
  // POST: return value is the numerator of this instance
  int numerator() const {
    return n;
  }
  // POST: set numerator of this instance to value
  void set_numerator(int value) {
    n = value;
  }
  // POST: return value is the denominator of this instance
  int denominator() const {
    return d;
  }
  // PRE:  value != 0
  // POST: set denominator of this instance to value
  void set_denominator(int value) {
    assert(value != 0);
    d = value;
  }
private:
  int n;
  int d; // INV: d != 0
};

They are called with member access: r.set_denominator(1); int n = r.numerator();. Inside, n means the n of the object the function was called on, r. The scope of members is the whole class, so the private members may be declared after the functions that use them. set_denominator defends the invariant with an assert: no user can make d zero any more (except at the very start, which section 6 fixes).

const member functions (p. 164): the const after the parameter list promises that the function doesn't change the object. A const object can only call const member functions. Behind the scenes, the object is an implicit argument named this, and n is short for this->n; this is a pointer (lesson 12). The const refers to that implicit argument.

Writing a class in five steps

  1. What are the values, and what is the invariant? Choose private members and write // INV: next to them.
  2. What can a user do with it? Each action is a public member function with PRE and POST.
  3. Does the function change the object? No: add const after the parameter list. Getters are const, setters are not.
  4. How is an object made? A constructor that establishes the invariant, with a member initializer list (section 6). Need T t; to compile? Then also a default constructor.
  5. Can any public function break the invariant? Check each one that changes members; defend with an assert or a PRE.

Worked example 2: const objects (script p. 164)

With the class above:

rational x;
x.set_numerator(10);      // (1)
const rational y = x;
int n = y.numerator();    // (2)
y.set_numerator(10);      // (3)
  1. Which lines compile?
    Answer

    (1) and (2). (3) is an error: y is const, and set_numerator is not a const member function.

  2. What if numerator() had no const?
    Answer

    Then (2) would be an error too, although numerator changes nothing: the compiler only trusts the promise, not the body. So mark every function that doesn't change the object const. That matters for const references too: in void print(const rational& r), only const members can be called on r.

  3. Could a const member function call set_numerator on its own object?
    Answer

    No: inside a const member function the object itself is const. This is exactly the third error in exercise 1.

6. Constructors (script 13.4)

To defend an invariant, it must hold in the first place. Constructors are special member functions named like the class, with no return type, called whenever an object is created (p. 165). Like functions, they can be overloaded; the compiler picks the best match, and if none fits, it reports an error.

class rational {
public:
  rational(int num, int den) : n(num), d(den) {
    assert(d != 0);
  }
  // ...
};

rational r = rational(2, 3);  // r = 2/3
rational s(1, 2);             // s = 1/2

After the parameter list and a colon comes the member initializer list: it initializes the members before the body runs (p. 166). Then the body checks the invariant.

The default constructor is the one with no parameters. It is called for rational r;, and if it doesn't exist, that line doesn't compile. If a class has no constructors at all, the compiler generates one, which leaves fundamental members uninitialized. Writing your own fixes that:

rational() : n(0), d(1) {}   // rational r;  is now 0/1

Or forbid rational r; altogether with rational() = delete; (p. 166–167). Either way, there are no uninitialized rationals any more.

User-defined conversions (p. 167): a constructor with one parameter converts. With rational(int num) : n(num), d(1) {}, both rational r = rational(2); and rational s = 2; work. The other way, from rational to double, needs a conversion operator, a member function with no return type written: operator double() { return double(n) / d; }, so that double b = a; works.

The script also lists the many forms of initialization C++ allows, T t(…), T t{…}, T t = T(…) and others (p. 167–169). You don't need to know their differences. The course's convention: int i = 5; for literals, rational half = {1, 2}; for structs with only public members, and rational half = rational(1, 2); otherwise.

Worked example 3: which constructor is called?

A class has rational(), rational(int num) and rational(int num, int den), all public.

  1. rational a;   rational b = rational(3);   rational c = 3;   rational e(3, 4);
    Answer

    a: the default constructor, 0/1. b and c: rational(int), 3/1 (c by implicit conversion). e: rational(int, int), 3/4.

  2. rational f(3, 0);?
    Answer

    Compiles, but the assert in the constructor fails at run time: the program stops before an invalid object can exist.

  3. If the class had only rational(int num, int den), which of a, b, c, e compile?
    Answer

    Only e. Once you write any constructor, the compiler no longer generates the default constructor, so rational a; fails; and there is no one-parameter constructor for b and c.

7. Member definitions outside the class (script 13.5)

To keep the class short, or to put it into a header, declare the member functions in the class and define them outside, with the class name and the scope operator :: (p. 169–170):

// declaration (rational.h)
class rational {
  int n;
  int d;
public:
  int numerator() const;
  void set_numerator(int value);
};

// definitions (rational.cpp)
int rational::numerator() const {
  return n;
}
void rational::set_numerator(int value) {
  n = value;
}

The const must appear in both places. Without rational::, int numerator() const { … } would be a new free function, and the compiler would complain that a free function can't be const and that n is unknown.

Here is the whole class at work: the invariant is checked once in the constructor and can't be broken from outside. Coding task 2 makes it stronger: always in lowest terms.

#include <cassert>
#include <iostream>

class rational {
  int n;
  int d; // INV: d != 0
public:
  rational(int num, int den) : n(num), d(den) {
    assert(d != 0);
  }
  rational() : n(0), d(1) {}
  int numerator() const { return n; }
  int denominator() const { return d; }
};

int main() {
  rational r = rational(2, 3);
  rational z;
  std::cout << r.numerator() << "/" << r.denominator() << "\n";
  std::cout << z.numerator() << "/" << z.denominator() << "\n";
  return 0;
}

Coding task 1: a checksum class (IFMP August 2015, task 7, official exam, 6 points)

A checksum is computed from a series of values and is used to check their integrity. Complete the class: (1) the constructor initializes sum with 0; (2) add adds a natural number to sum; (3) get returns sum without changing it. The exam asked for five gaps: the access keyword, the initializer, the statement in add, the places where const may go, and the return expression.

You'll need these

public: (section 4), const member functions (section 5), the member initializer list (section 6).

What the contract forces (before any idea)
  • Given: the private member sum; main creates Checksum cs; and calls cs.add(…) and cs.get().
  • Must hold at the end: get() returns the sum of all added values, 0 if none.
  • The gap to fill: what must be public, how sum starts at 0, and which functions promise not to change the object.

    My answer

    public (official). Without it, everything in a class is private, and main could neither create a Checksum (the constructor would be private) nor call add.

  2. (b), (c), (e): the initializer, the statement in add, the return.
    My answer

    sum(0), sum += value, sum (all official).

  3. (d) The exam marked four places D1 to D4: before unsigned int sum, before the parameter of add, after add's parameter list, after get's parameter list. Where may const go?
    My answer

    D2 and D4 (official). D2: add doesn't change its own copy of value. D4: get doesn't change the object. D1 would make sum unchangeable, so sum += value fails; D3 would promise that add doesn't change the object, but it does.

Coding task 2: rationals in lowest terms (script Section 13.1)

The script wishes for rationals that are "always stored in a reduced form" (p. 161). With a class, that is a constructor's job. Write the constructor so that the invariant "d > 0 and n/d in lowest terms" holds for every object; the rest of the program relies on it.

You'll need these

Constructors with an initializer list and assert (section 6), the gcd from lesson 7 (given), and the operators of lesson 9.

What the contract forces (before any idea)
  • Given: two integers num and den with den ≠ 0.
  • Must hold at the end: the object has the value num/den, d > 0, and gcd(|n|, d) = 1. So 2/4 is stored as 1/2, 1/−2 as −1/2, 0/7 as 0/1.
  • The gap to fill: fix the sign first, then divide both by the gcd.

Try it yourself: write the body of the constructor, then press Check.

#include <cassert>
#include <iostream>

// POST: returns the greatest common divisor of a and b (gcd(0, 0) = 0)
int gcd(int a, int b) {
  if (b == 0) return a;
  return gcd(b, a % b);
}

class rational {
  int n;
  int d; // INV: d > 0 and n / d is in lowest terms
public:
  // PRE:  den != 0
  // POST: *this is num / den, stored in lowest terms with d > 0
  rational(int num, int den) : n(num), d(den) {
    assert(den != 0);
    // todo
  }

  // POST: *this is 0
  rational() : n(0), d(1) {}

  int numerator() const { return n; }
  int denominator() const { return d; }
};

// POST: returns a + b
rational operator+(rational a, rational b) {
  return rational(a.numerator() * b.denominator() + a.denominator() * b.numerator(),
                  a.denominator() * b.denominator());
}

// POST: r has been written to out as n/d
std::ostream& operator<<(std::ostream& out, rational r) {
  return out << r.numerator() << "/" << r.denominator();
}

int main() {
  int a, b, c, d;
  char slash;
  std::cin >> a >> slash >> b >> c >> slash >> d;
  rational r = rational(a, b);
  rational s = rational(c, d);
  std::cout << r << " + " << s << " = " << r + s << "\n";
  return 0;
}
  1. Why does operator+ not need to reduce?
    My answer

    It builds its result with the constructor, and the constructor reduces. Every rational, however made, goes through the factory door. That is the point of the class.

  2. Why can operator+ not simply write a.n?
    My answer

    n is private and operator+ is a free function, not a member. It uses the public getters.

  3. The order: sign or gcd first? And what about 0/7?
    My answer

    Either order works if gcd gets non-negative numbers: take |n| for the gcd. For 0/7: gcd(0, 7) = 7, so 0/7 becomes 0/1. The gcd is never 0 here, because d ≠ 0.

  4. Write it.
    Answer (written by StudyHub, checked by compiling)

    Frame: after the initializer list, the body brings (n, d) into the one standard form.

    The golem's stepsWhat you write

    If the bottom number is negative, flip both signs: the value stays, the bottom becomes positive.

    if (d < 0) {
  n = -n;
  d = -d;
}

    Find the largest number that divides both, and divide it out.

    int g = gcd(n < 0 ? -n : n, d);
n = n / g;
d = d / g;
    The program in one piece
    #include <cassert>

  if (b == 0) return a;

}

class rational {
  int n;
  int d; // INV: d > 0 and n / d is in lowest terms
public:
  // PRE:  den != 0
  // POST: *this is num / den, stored in lowest terms with d > 0
  rational(int num, int den) : n(num), d(den) {
    assert(den != 0);
    if (d < 0) {
      n = -n;
      d = -d;
    }
    int g = gcd(n < 0 ? -n : n, d);
    n = n / g;
    d = d / g;
  }

  // POST: *this is 0
  rational() : n(0), d(1) {}

  int numerator() const { return n; }
  int denominator() const { return d; }
};

  return rational(a.numerator() * b.denominator() + a.denominator() * b.numerator(),
                  a.denominator() * b.denominator());
}

// POST: r has been written to out as n/d
std::ostream& operator<<(std::ostream& out, rational r) {
  return out << r.numerator() << "/" << r.denominator();
}

  5. Tests.
    My answer

    Already reduced inputs; inputs that need reducing (2/4); a negative denominator (1/−2); a sum that is 0, which must print as 0/1; a zero input 0/7; a sum that reduces (1/6 + 1/3 = 3/6 = 1/2); and whole numbers.

  6. What does == look like now?
    My answer

    Because every value has exactly one stored form, member-wise comparison is correct: a.numerator() == b.numerator() && a.denominator() == b.denominator(). The stronger invariant made equality simpler, which lesson 9 warned was wrong for the struct.

  3. Free functions use the public interface only.

In short: "invariant once, at the door".

Coding task 3: inverting an image (after the Informatik exam winter 2013/14, task 5, 14 points)

A class for 7 × 7 black-and-white images. The exam asked for the default constructor (an empty, all-white image), set_pixel(r, c) (make one pixel black), and operator!, which returns the inverted image, black and white swapped. The exam stored a two-dimensional array; we use a vector of vectors (lesson 5). The output operator and is_black are given.

You'll need these

A 7 × 7 std::vector<std::vector<bool>> and nested loops (lesson 5); the initializer list; a const member function that builds a new object of its own class.

    My answer

    It doesn't change *this: it makes a new local image result, fills it from its own pixels, and returns it. Writing result.bitmap is allowed: private means private to the class, so a member function may touch the private members of any object of its class.

Coding task 4: a temperature that hides its scale (script Section 13.1)

The third wish of section 3: change the representation without changing user code. This class stores kelvin, but its users only ever see degrees Celsius and Fahrenheit. The invariant is physical: no temperature below absolute zero.

You'll need these

Constructor with assert (section 6), const getters, and $F = C \cdot 9/5 + 32$, $K = C + 273.15$.

What the contract forces (before any idea)
  • Given: a start temperature in Celsius ≥ −273.15, then commands "warm x" and "cool x".
  • Must hold at the end: kelvin ≥ 0 always; celsius() and fahrenheit() report the current value without changing it.
  • The gap to fill: converting between the hidden kelvin and the public scales, in one place each.

Try it yourself: write the bodies, then press Check.

#include <cassert>
#include <iostream>
#include <string>

class temperature {
  double kelvin; // INV: kelvin >= 0
public:
  // PRE:  c >= -273.15
  // POST: *this is c degrees Celsius
  temperature(double c) : kelvin(0) { // todo
  }

  // POST: returns the temperature in degrees Celsius
  double celsius() const {
    return 0; // todo
  }

  // POST: returns the temperature in degrees Fahrenheit
  double fahrenheit() const {
    return 0; // todo
  }

  // PRE:  celsius() + delta >= -273.15
  // POST: the temperature is delta degrees higher
  void warm(double delta) {
    // todo
  }
};

int main() {
  double start;
  std::cin >> start;
  temperature t = temperature(start);
  std::string command;
  double delta;
  while (std::cin >> command >> delta) {
    if (command == "warm") t.warm(delta);
    else if (command == "cool") t.warm(-delta);
  }
  std::cout << t.celsius() << " C = " << t.fahrenheit() << " F\n";
  return 0;
}
  1. Which functions are const?
    My answer

    celsius and fahrenheit only read; warm changes kelvin, so it isn't.

  2. Why does fahrenheit() call celsius()?
    My answer

    Then the kelvin offset 273.15 appears in exactly two places: the constructor (in) and celsius (out). If we later store Celsius instead, only those two change, and fahrenheit and all users stay as they are.

  3. Where can the invariant break?
    My answer

    In the constructor and in warm with a negative delta. Both get an assert(kelvin >= 0). The getters can't break it: they are const.

Worked example 5: a const member variable (IFMP August 2015, task 7 (d), continued)

  1. Why does const unsigned int sum; (marking D1) break the checksum class, although sum(0) in the initializer list still works?
    Answer

    A const member can be initialized (the initializer list runs before the body) but never assigned afterwards. sum += value is an assignment: error.

  2. And what is the difference between void add(const unsigned int value) and void add(unsigned int value) const?
    Answer

    The first promises not to change the parameter, a local copy, which is harmless and allowed. The second promises not to change the object, which add breaks: error.

class rational {

Exercise 1 (Informatik exam summer 2010, task 5, old exam) · 25 points

Given the following implementation of a class Clock:

01: class Clock {
02:   public:
03:     Clock(const unsigned int h,
04:           const unsigned int m,
05:           const unsigned int s) const
06:           : h_(h), m_(m), s_(s)
07:     {
08:     }
09:
10:     tick()
11:     {
12:       h_ += (m_ += (s_ += 1) / 60) / 60;
13:       h_ %= 24;
14:       m_ %= 60;
15:       s_ %= 60;
16:     }
17:
18:     void time(unsigned int& h,
19:               unsigned int& m,
20:               unsigned int& s) const
21:     {
22:       h = h_;
23:       m = m_;
24:       s = s_;
25:       tick();
26:     }
27:
28:   private:
29:     unsigned int h_;
30:     unsigned int m_;
31:     unsigned int s_;
32: };

(a) Describe briefly the purpose of the member variables h_, m_ and s_, of the methods tick() and time(…), and of the constructor. (6 points)

(b) Three errors in the class already cause compile errors. Name where they are and explain the problem. (6 points)

(c) The constructor's body is empty. Does that mean the constructor does nothing? At most two sentences. (4 points)

(d) Implement the global function std::ostream& operator<<(std::ostream& o, const Clock& c) that writes the time stored in c in the format h:m:s (no leading zeros needed). (9 points)

Hint 1

For (b), read each function head: what a constructor may not have, what every function must have, and what a const function may not call.

Hint 2

For (d), the output operator is a free function: it can't read h_. Which public member function hands the time out? And it gets a const clock.

Solution

Frame: (a) and (c): what each member does for the invariant "h_ < 24, m_ < 60, s_ < 60"; (b) the const and type rules of sections 5 and 6; (d) the output pattern of lesson 9 through the public interface. No official solution exists; written by StudyHub, errors confirmed by compiling.

(a) h_, m_, s_ store the current time: hours (0–23), minutes and seconds (0–59). tick() advances the clock by one second, with carries into minutes and hours and a wrap after 23:59:59. time(h, m, s) hands the stored time out through its three reference parameters. The constructor sets the clock to the time h:m:s.

(b) Line 5: a constructor can't be const (it must initialize the object). Line 10: tick() has no return type; it must be void tick(). Line 25: time is a const member function, but calls tick(), which changes the object and isn't const. (The compiler: "constructors may not be cv-qualified", "forbids declaration of 'tick' with no type", "passing 'const Clock' as 'this' argument discards qualifiers".)

(c) No: the member initializer list : h_(h), m_(m), s_(s) initializes the three members before the (empty) body runs. Nothing more needs to happen.

(d) With line 25 removed:

// POST: the time stored in c has been written to o in the format h:m:s
std::ostream& operator<<(std::ostream& o, const Clock& c) {
  unsigned int h, m, s;
  c.time(h, m, s);
  return o << h << ":" << m << ":" << s;
}

Points: local variables, the call to the const member time (the only legal way to read the private time from outside), the format, returning the stream.

Exercise 3 (out-of-class definitions) · 3 points

The class declares int numerator() const; and void set_numerator(int value);. What is wrong with each definition? (1 point each)

(a) int numerator() const { return n; }   (b) int rational::numerator() { return n; }   (c) void rational::set_numerator(int value) const { n = value; }

Solution

Frame: the definition must repeat the class name with :: and exactly the declaration's head.

(a) rational:: is missing: this is a new free function, which can't be const and doesn't know n. (b) The const is missing: the definition doesn't match the declaration. (c) The definition adds const, which doesn't match, and a const function couldn't assign n anyway.

Exercise 4 (true or false) · 4 points

  1. A struct can have private members and member functions.
  2. A const member function may read private members.
  3. If a class has a constructor rational(int, int) and no other, rational r; compiles.
  4. The member initializer list runs after the constructor's body.
Solution

Frame: sections 4 to 6, one rule each.

1. True: struct and class differ only in the default access (p. 161). 2. True: const forbids changing, not reading. 3. False: with any constructor written, no default constructor is generated (p. 166). 4. False: before (p. 166).

Summary: what to keep from lesson 10

  • Information hiding: offer functionality, not representation. Benefits: invariants hold, users see the "what", the "how" can change.
  • class = struct with private as default. public: members are usable everywhere, private: ones only inside the class (in any object of that class).
  • Member functions are called as r.f() and see the members of r. const after the parameter list: doesn't change the object; const objects and const references can only call these.
  • Constructors: named like the class, no return type, member initializer list before the body; they establish the invariant. A default constructor makes T t; possible; it is generated only if you write no constructor at all.
  • One-parameter constructors convert implicitly; operator double() converts the other way.
  • Outside the class: int rational::numerator() const { … }, head exactly as declared.

For wonder: the 125-million-dollar unit (optional, 5 min)

In September 1999, NASA's Mars Climate Orbiter burned up in the Martian atmosphere. The investigation board found that one team's ground software reported thruster impulses in pound-force seconds, while the navigation software expected newton seconds, a factor of about 4.45. Both programs passed plain numbers to each other; nothing in the type said which unit was meant. Over the nine-month cruise the small errors added up, and the orbiter came in far too low. Coding task 4 is the cure in miniature: a temperature object has no unit visible from outside, only celsius() and fahrenheit(), so mixing scales is impossible by construction. Libraries that put physical units into types work the same way, and turn such mistakes into compile errors.
