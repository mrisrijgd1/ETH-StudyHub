1. The story: the literal golem

At the edge of the old kingdom, past the gardens of the Analysis surveyors and the guild halls of the Free City, stands a workshop with a clay golem in it. The golem is tireless and unbelievably fast: it can carry out billions of small orders per second. But it has no common sense at all. It does exactly what its scroll says, line by line, from top to bottom, and nothing else.

Along the walls are shelves of boxes. Each box has a label and holds one value. When the scroll says "put 5 into the box a", the golem does it. When it says "read box b", it reads whatever is in there, even if nobody ever put anything in. Some boxes sit behind glass: you can read them, but no order can change them.

Before any scroll reaches the golem, it passes the gatekeeper. The gatekeeper knows the grammar of the scroll language by heart. A missing semicolon, a box that was never made, a value that does not fit a box: the scroll is sent back with a note. But the gatekeeper only checks the grammar. A perfectly written scroll that asks for the wrong thing passes, and the golem will carry it out faithfully, wrong as it is.

You are the new scroll-writer. Your job in this course is to think a solution through, write it so that the gatekeeper lets it pass, and be sure that the golem, doing exactly what you wrote, does what you meant.

In computer science: the golem is the computer (the processor), the scroll is the program, the boxes are variables in memory (the script draws them as boxes too, p. 21 and 28), the boxes behind glass are constants, and the gatekeeper is the compiler, which rejects syntax errors but cannot judge the semantics, what your program means. That last point is the heart of the course: a program that compiles is not yet a correct program.

2. The task method: how to start any programming task

Most people who get stuck in this course don't lack C++. They open the editor, look at the empty main, and have no structure for what to do next. The course's TAs answer this in their C++ Guides ("Approaching Programming Tasks"): a programming task is two tasks, (1) find an algorithm, then (2) write it in C++, and you should finish the first before starting the second. Here is their advice as questions you ask yourself, in order. Every coding task on this site uses them.

The six questions

  1. What goes in, what comes out? Write the contract in one line: the input (what type, which range), the output (exact format). Example: "in: one int a; out: the line 29 * a = …".
  2. Can I solve two or three examples by hand? On paper, with small numbers. Pay attention to how you do it. Make it small on purpose: if the task is about overflow, pretend an int has 4 bits.
  3. What were my steps? Write them in plain words or pseudo-code. Look for steps that are "magic" (obvious to you, but not one C++ operation). Refine each magic step until none are left.
  4. Does my plan survive another example, including an edge case? Run the plan by hand on a new input: 0, a negative number, the smallest or largest allowed input. Most hidden tests live here.
  5. Which pattern do I know that does this? Translate step by step. Start with the frame read input · compute · print output, and reuse patterns you know (swapping two variables, summing in a loop, …). This lesson's patterns are in the summary at the end.
  6. How do I know it works? Run it on the task's examples and on your own: ordinary cases, boundary cases, the edge case from question 4. A passing test is evidence, not proof.

Source: the course's C++ Guides, "Approaching Programming Tasks" and "The Use of AI" (test advice). The questions are StudyHub's wording of their steps. The full method with examples is on the Task method page.

You'll use the six questions for the first time in Coding task 1, after you know enough C++ to write one line of it.

3. Algorithms: orders without intelligence

The script defines computer science as "the automation of intellectual activities" (p. 8) and puts the algorithm at its heart:

Algorithm (script p. 8–9): a series of instructions to solve a problem step by step. Its execution does not require any intelligence, only precision, so even a computer can do it.

A recipe is an everyday algorithm. The oldest non-trivial one in mathematics is Euclid's algorithm for the greatest common divisor (script p. 9–10). Its core idea: the common divisors of $a$ and $b$ are the same as those of $a-b$ and $b$ (if $c\mid a$ and $c\mid b$ then $c\mid a-b$, and back, since $a=(a-b)+b$). So you may keep replacing the larger number by the difference without changing the gcd. The numbers shrink every step, so it stops, and when $a=b$ the gcd is $a$ itself.

The script shows the same algorithm on three levels of abstraction (p. 10–11):

  1. Core idea (the "eureka" sentence above, for humans).
  2. Pseudo-code (semi-detailed, for humans to check correctness and discuss it):
Input:  two strictly positive integers a, b
Output: greatest common divisor of a and b
while a ≠ b do
    if a > b then a ← a − b
    else          b ← b − a
end
Result: a
  1. Implementation (fully detailed, for humans and the computer). Here is the C++ version, which you'll be able to read completely after lesson 3:
#include <iostream>

int main() {
  int a = 12;           // the two lengths
  int b = 8;
  while (a != b) {      // as long as they differ
    if (a > b) {
      a = a - b;        // shorten the longer one
    } else {
      b = b - a;
    }
  }
  std::cout << a << "\n"; // gcd(12, 8)
  return 0;
}
4

Notice the arrow $a\leftarrow a-b$ in the pseudo-code: the variable $a$ changes its value over time. In mathematics we would write $a_1, a_2, \dots$; in programming, one name holds different values one after another. The script points this out on p. 9 as the thing "you might not have seen before". It is the single most important habit to get used to.

Worked example 1: run Euclid by hand with $a=12$, $b=8$

Try it in your head first. Keep a table with one column per variable and write each new value below the old one.

  1. First check: is $a\ne b$? Which branch runs, and what are the new values?
    Answer

    $12\ne8$ and $12>8$, so $a\leftarrow12-8=4$. Now $a=4$, $b=8$.

  2. Continue until the loop stops.
    Answer
    stepabwhy
    start128input
    14812 > 8, so a ← 12 − 8
    2444 < 8, so b ← 8 − 4
    stop44a = b: result 4

    $\gcd(12,8)=4$. ✓

  3. Why is this slow for $a=100$, $b=12$, and what is the fix the script mentions?
    Answer

    It subtracts 12 eight times in a row (100, 88, …, 4). Eight subtractions of the same number are one division with remainder: replace $a-b$ by $a \bmod b$. That is the faster version (script p. 12, footnote 1); you'll write it in lesson 3.

What the golem really does: the box computer

To understand the step from pseudo-code to the machine, the script invents a box computer (p. 11–12): numbered boxes (memory locations, the numbers are addresses) that hold either instructions or data, plus two fast registers L and R. The instructions are tiny: copy a box into a register, compare, subtract, jump to another box. Boxes 0 to 7 hold Euclid's algorithm; boxes 8 and 9 hold $a$ and $b$. If you play the machine yourself with 12 and 8 (the script invites you to), you'll find that you need no understanding at all, only precision. That is exactly the point of an algorithm, and exactly what the golem is.

Real computers follow the same plan, the von Neumann architecture (p. 13–14, marked * in the script, so background only): memory (RAM) where every cell has an address and holds programs and data, a processor (CPU) with a few very simple instructions and its own fast registers, and input/output. Today's laptops execute hundreds of billions of instructions per second.

4. Languages, syntax and semantics

The machine only understands machine language: very primitive, different for each processor. So we write in a programming language (here C++), and a compiler translates the program text into machine code (script p. 15, Figure 1.7). The script compares two kinds of rules (p. 16–17):

Syntax

The rules for how symbols may be put together: is this a C++ program at all? Checked by the compiler, completely and automatically. A missing ; is a syntax error, and the compiler refuses to translate.

Semantics

The rules for what a program means: which algorithm does it carry out? The compiler can catch some semantic errors, but in general this needs human understanding.

So a program can go wrong in two places (script p. 17):

  • At compile time: the compiler reports errors (no program is produced) or warnings (a program is produced, but something looks suspicious; never ignore them).
  • At run time, a compiled program can give the correct result, give a wrong result, crash, or never terminate.

That is why the script calls the compiler "our friend": every error it catches early is one you don't have to hunt down at run time. Why C++? It makes you take decisions explicitly (types, memory), "like getting a driver's license for manual transmission, and driving automatic later" (p. 15–16).

5. Anatomy of a C++ program

Here is the script's first program (Code 2.1, p. 18), with a comment on every line:

// Program: power8.cpp
// Raise a number to the eighth power.
#include <iostream>   // make std::cin, std::cout available

int main() {          // the program starts here
  // input
  std::cout << "Compute a^8 for a = ? "; // print a prompt
  int a;              // a box a for an int (still empty)
  std::cin >> a;      // read a number into a

  // computation
  int b = a * a;      // b = a^2
  b = b * b;          // b = a^4 (b changes!)

  // output b * b, i.e., a^8
  std::cout << a << "^8 = " << b * b << "\n";
  return 0;           // end: 0 means "all went well"
}

Entering 2 gives:

Compute a^8 for a = ? 2^8 = 256

(On a real console the 2 you type appears after the prompt and your Enter key starts a new line, so you see Compute a^8 for a = ? 2, then 2^8 = 256, as in the script.)

The parts, from the script (p. 19):

  • int main() { … }, the main function: the entry point, called by the operating system when the program starts. Its contents run from top to bottom, one statement after another.
  • Statements are the orders to the golem. Almost every statement ends with a semicolon. Write one statement per line.
  • Comments start with // and run to the end of the line (or sit between /* and */). The compiler ignores them; they are for humans.
  • #include <iostream> makes input/output from the standard library available. Without it, the compiler stops with an error such as "no member named 'cout' in namespace 'std'" (p. 20). Note: no semicolon after an include.
  • return 0; ends main; the 0 tells the operating system that all went well.

Layout does not matter to the compiler (you could write the whole program on one line, p. 19) but it matters to every human who reads it, including you next week. Indent the inside of every { }.

Output with std::cout

std::cout << x prints the value of x on the console (p. 20–21). You can print numbers, text in double quotes, and the result of a computation, and you can chain several << in one statement. Text is printed exactly as written: no space and no new line are added for you. A new line comes only from "\n".

#include <iostream>

int main() {
  std::cout << "the eighth power of two:\n";
  // 8 factors 2; C++ computes it for us:
  std::cout << "2^8 = " << 2*2*2*2*2*2*2*2;
  std::cout << "!" << "\n";  // continues the line
  return 0;
}
the eighth power of two:
2^8 = 256!

6. Variables: boxes with a type, a name and a value

A variable is a box that stores a value (script p. 21). Every variable has four things: a type (which values fit, and which operations work), a name (letters, digits and _, starting with a lower-case letter by convention), a current value, and an address (where in memory the box is; the compiler picks it). The first types you need:

typeformaths
intintegers$\mathbb Z$ (a finite part of it)
unsigned intnatural numbers$\mathbb N$ (a finite part)
float, doublereal numbers (approximately)$\mathbb R$ (with holes)

The exact limits ("a finite part", "with holes") are lesson 2. Three ways of putting a value into a box:

int x;      // declaration: make a box x (value undefined!)
x = 2;      // assignment: put 2 into x
int y = 3;  // declaration with initialization
int z = x + y;  // initialize with an expression: 5
int u, v;   // two boxes of the same type at once

The rule for every assignment (p. 22): first evaluate the right-hand side (replace each variable name by its current value), then store the result in the box on the left.

How to trace a program: the variable table

This is the course's tracing method (C++ Guides, "Tracing"), and it is how you answer every "What does this print?" question. Keep a table with a row per variable and one output line. Go statement by statement:

  1. Declaration int a;: add a row a with an empty value. Empty means uninitialized; reading it is a bug.
  2. Assignment a = …;: evaluate the right side with the values in the table, then cross out the old value of a and write the new one next to it.
  3. Output std::cout << …;: append exactly what is printed to the output line. Output can only grow.
  4. Check: if a statement uses a name with no row, or reads an empty value, stop: that program has a bug.

Check your table afterwards with C++ Tutor (pythontutor.com, choose C++), as the Guides suggest. Its "Stack" table is your variable table.

    Answer

    After a = b; the old value 5 of a is gone (crossed out), so b = a; copies 3 back. Both end as 3. The helper box keeps the old value safe. This is the swap pattern, the first programming pattern of the Guides; you'll meet it again in sorting.

Pitfalls with variables

The script lists six (p. 22–25). Each one is a classic exam trap, so here they all are, each with what the compiler or the golem does.

Attention, trap (script p. 23)

The assignment operator = is the mathematical :=, not the comparison $=$. So x = 2; x = 3; is fine (x is now 3), and x = x + 1; means "read x, add 1, store the result in x". In mathematics $x=x+1$ never holds; in C++ it is the most common line there is. Comparison in C++ is written == (lesson 2).

7. Input, and the frame of every program

Hard-coding the input (int x = 2;) means changing the program for every new number. Instead, std::cin >> x waits for the user to type a value and stores it in x (p. 25). With it, almost every program in this course has the same frame, which the Guides call a meta-level pattern:

int main() {
  // 1. read the input
  // 2. compute the result
  // 3. print the result
  return 0;
}

The script's second version of power8 (p. 25) fills the frame with one well-named variable per intermediate result instead of reusing b. Both versions compile to equivalent programs; choose whichever is easier to read (p. 26).

#include <iostream>

int main() {
  // 1. input
  int x;
  std::cout << "Compute a^8 for a = ? ";
  std::cin >> x;
  // 2. computation: one name per step
  int x_squared = x * x;                  // x^2
  int x_to_the_four = x_squared * x_squared; // x^4
  int x_to_the_eight =
      x_to_the_four * x_to_the_four;      // x^8
  // 3. output
  std::cout << x << "^8 = " << x_to_the_eight << "\n";
  return 0;
}

Coding task 1: multiply by 29 with additions only (Code Expert, Exercise 1, Task 2)

Read an integer a and print 29 * a, using only additions and assignments: no *, no loops. Use as few additions as you can (the task allows at most 27). This is the first time we use the six questions, so each one is folded out below. Try to answer each yourself before opening it.

What the contract forces (before any idea)
  • Given: one int a, read from the input.
  • Must hold at the end: the line 29 * a = r is printed with $r=29a$.
  • Allowed: + and = only.
  • The gap to fill: reach $29a$ from $a$ in few additions.

Try it yourself. The input and output lines are already there; fill in the computation and press Check. (The tests can only see the result: that you used no * is yours to check.)

#include <iostream>

int main() {
  // input
  std::cout << "a = ? ";
  int a;
  std::cin >> a;

  // computation: only + and = allowed
  int result = 0;   // replace this line

  // output
  std::cout << "29 * " << a << " = " << result << "\n";
  return 0;
}
  1. What goes in, what comes out?
    My answer

    In: one int a. Out: $29a$, printed. Restriction: only + and =.

  2. Can I solve examples by hand? Compute $29\cdot 3$ using only additions, and count them.
    My answer

    The naive way, $3+3+\dots+3$, takes 28 additions: too many. Better: doubling. $3+3=6=2\cdot3$, $6+6=12=4\cdot3$, $12+12=24=8\cdot3$, $24+24=48=16\cdot3$. Now write 29 in powers of two: $29=16+8+4+1$. So $29\cdot3=48+24+12+3=87$. ✓ That took $4+3=7$ additions.

  3. What were my steps?
    My answer

    Double four times to get $2a, 4a, 8a, 16a$ (4 additions). Then add the parts that make 29: $16a+8a+4a+a$ (3 more). 7 additions in total. No magic step left: each step is one +.

  4. Does it survive another example, an edge case?
    My answer

    $a=0$: every step gives 0, result 0 ✓. $a=-1$: $-2,-4,-8,-16$, then $-16-8-4-1=-29$ ✓. Negative numbers work, because doubling works for them too.

  5. Which pattern? Write the code in the input · compute · output frame.
    My answer (written by StudyHub, compiled and tested)

    Every intermediate value is a const, because none of them changes after it is computed (section 9 explains why that is good style).

  6. How do I know it works?
    My answer

    Test 3 (87), 0 (0), −1 (−29), 1 (29), and a big one like 1000 (29000). In Code Expert, run the visible tests too. Could 6 additions be enough? No: with $k$ additions the largest multiple you can reach is $2^k a$, and the numbers reachable in 6 steps do not include 29 (mathematicians call this the length of the shortest addition chain, which is 7 for 29). So 7 is optimal.

Patterns used: input · compute · output one named const per step

How to write this under exam pressure
  1. Write 29 in powers of two: 16 + 8 + 4 + 1.
  2. Double up to the largest power: a2, a4, a8, a16 (one addition each).
  3. Add the needed powers: a16 + a8 + a4 + a.
  4. Test 0 and a negative number before submitting.

In short: "binary digits of the factor, doubling, then add".

Your turn: the coding ladder

    Answer

    $13=8+4+1$, so double three times (a2, a4, a8) and write const int result = a8 + a4 + a;: 5 additions.

8. Expressions, statements and effects

We've been using expressions all along: a * a, x + 2, 3. The script's definition (p. 26):

Expression. An expression represents a computation. It has a fixed type, a (time-dependent!) value, and possibly an effect. The type is known when compiling; value and effect are determined only when the expression is evaluated while the program runs.

  • Primary expressions: a literal (2, with type int and value 2; 1.2e5, type double, value 120000) or a variable name.
  • Composed expressions: built from expressions with operators and parentheses, like x * 3. An operator combines operands: a unary operator takes one (-x), a binary operator two (x * 3). The operator fixes how many operands and of which types: 3 % 2.5 does not compile, because % needs two integers.

Writing an expression followed by ; makes it an expression statement: "evaluate this". That is only useful when the expression has an effect. And here is the surprise of chapter 2 (p. 27–28): you've been writing such expressions all along.

  • Assignment is an expression. x = y has an effect (store y's value in x), and its value and type are those of the left side after storing. So std::cout << (x = y); prints 2 if y is 2, and x = (y = 3); sets both to 3. Legal, but please don't: it invites bugs.
  • << and >> are operators with effects: std::cout << x has the effect "print x" and the value std::cout. That value is why you can chain: (std::cout << a) << b.
Exam answer, IFMP August 2016, task 1a (official solution)

"Every expression has a type." True. The type is fixed at compile time, for every expression, even x = y and std::cout << x.

9. Constants: boxes behind glass

Some values must never change, like the speed of light. Writing const in front of the type makes a constant: it must be initialized, can be read, and any attempt to assign to it is a compiler error (p. 28–29).

const int speed_of_light = 299792458; // m/s
std::cout << speed_of_light;  // reading: fine
speed_of_light = 300000;      // compiler error

Const guideline (script p. 29). For each variable, think about whether it will change its value during the program. If not, declare it const. A program that follows this is called const-correct.

Why bother? Because accidental changes happen far more often than you'd think, and with const the gatekeeper catches them before the golem ever runs. Every error the compiler finds is one you don't debug.

Why it's cool

The box computer of section 3 knows a handful of tiny instructions: copy, compare, subtract, jump. Turing proved in 1936 that a machine this simple, given enough tape, can carry out every computation that can be written as an algorithm at all (script p. 12–13). Your phone, a weather simulation, a chess engine: all of them are, in principle, the golem following very small orders very fast. Everything else in this course is about writing those orders well.

    Answer

Worked example 4: does it compile, and if yes, what is the value?

For each line (separately, with int a = 1, b = 2; before it), decide: compiler error, or compiles with which result?

(a) a = b = 5; (b) 1 = a; (c) a + b = 3; (d) int c = 7.9; (e) int d; d = d + 1;

  1. Which of them try to assign to something that is not a box?
    Answer

    (b) and (c): 1 and a + b are rvalues (no address). Both are compiler errors.

  2. And the other three?
    Answer

    (a) compiles: it means a = (b = 5) (assignment is evaluated right to left, details in lesson 2), so both are 5. (d) compiles with a warning at most: c is 7 (cut towards 0). (e) compiles, but reading d before it has a value is undefined behavior: the program is wrong even though the compiler accepts it.

Coding task 2: seconds since midnight

Read three integers h m s (a time of day: hours 0–23, minutes and seconds 0–59) and print how many seconds have passed since midnight, as seconds since midnight: …. Use the six questions; the answers fold out.

What the contract forces (before any idea)
  • Given: three ints h, m, s with $0\le h\le23$, $0\le m,s\le59$.
  • Must hold at the end: the line seconds since midnight: t with $t$ the number of seconds from 00:00:00.
  • The gap to fill: turn hours and minutes into seconds.

Try it yourself in the editor, then press Check.

#include <iostream>

int main() {

  int h;

  int s;

  int total = 0;   // replace this line

  1. What goes in, what comes out?
    My answer

    In: three ints in the given ranges. Out: one line with one number. No restrictions on operators.

  2. Examples by hand. 01:00:00? 00:02:05? 23:59:59?
    My answer

    3600; $2\cdot60+5=125$; and $23\cdot3600+59\cdot60+59$ $=82800+3540+59$ $=86399$ (one second before the next midnight, $86400-1$: a good sanity check).

  3. Steps in words.
    My answer

    Each hour is 3600 s, each minute 60 s. Total $=3600h+60m+s$. One expression, no magic.

  4. Edge case?
    My answer

    00:00:00 gives 0 ✓. The largest value 86399 fits easily into an int (lesson 2: up to about 2.1 billion).

  5. Code.
    My answer (written by StudyHub, compiled and tested)

How to write this under exam pressure
  1. Units first: 1 h = 3600 s, 1 min = 60 s, as named constants.
  2. One formula: $3600h+60m+s$.
  3. Copy the output format exactly, colon and space included.
  4. Sanity check: 23 59 59 must give 86399.

Exercise 3 (find the errors) · 3 points

This program should read a side length and print the area of the square with that side. Find the three problems. For each: compiler error, warning, or undefined behavior?

#include <iostream>
int main() {
  int side;
  int Area = side * side;
  std::cin >> side;
  const int factor = 1;
  factor = 2;
  std::cout << area << "\n";
  return 0;
}
Hint 1

Read the program as the golem does: top to bottom. At each line, which boxes already hold a value?

Hint 2

One problem is about order, one about const, one about spelling. Only two of them stop the compiler.

Solution

Frame: for each line, ask: does the gatekeeper accept it (syntax, names, const), and if yes, does it read a box before it has a value?

  1. int Area = side * side; comes before std::cin >> side;, so it reads an uninitialized variable: undefined behavior (it compiles; the compiler may warn). Fix: read first, compute after. The golem runs top to bottom; the order of statements is the order of events.
  2. factor = 2; assigns to a constant: compiler error.
  3. area is not Area: names are case-sensitive, so area was never declared: compiler error.

Note that problem 1 is the dangerous one: the compiler accepts the program, so only a human who traces it in order finds the bug.

Exercise 4 (true or false, old exam style) · 4 points

(a) A program that compiles always terminates. (b) Comments change what the compiled program does. (c) After int x = -3.7; the value of x is −3. (d) x = y = 0; sets both x and y to 0.

Solution

Frame: each statement is about one rule of this lesson: compile vs run, comments, conversion to int, assignment as an expression.

(a) False. Compiling only checks syntax (and a few semantic things); at run time a program can still loop forever or crash (script p. 17). (b) False. The compiler ignores comments completely. (c) True. Conversion to int cuts towards 0 (script p. 23). (d) True. It is x = (y = 0); the inner assignment has value 0.

Summary: what to keep from lesson 1

  • An algorithm = steps that need precision, not intelligence. Three levels: core idea, pseudo-code, implementation.
  • Syntax (compiler checks) vs semantics (you check). Compiling ≠ correct.
  • A program = #include + int main() { statements; return 0; }, run top to bottom.
  • A variable = type + name + value + address. Assignment: evaluate the right, store on the left. = is :=.
  • Traps: rvalue on the left, misspelled names, uninitialized reads (undefined behavior), changing a const, << adds no spaces.
  • Patterns so far: input · compute · output; swap with a helper variable; one well-named const per intermediate result.
  • Method: the six questions for writing, the variable table for reading.

For wonder: the question no compiler can answer (optional, 5 min)

Exercise 4 (a) said a compiled program might never stop. Couldn't a clever compiler check for that, and warn us? Turing, the same man as the machine, proved in 1936 that no program can decide, for every program and input, whether it terminates. The idea is a paradox: if such a checker existed, you could build a program that asks the checker about itself and then does the opposite of the answer. This is why an old IFMP exam (August 2016, task 1c) could ask "There are compilers that detect whether every program is free from infinite loops" and expect false. The gatekeeper is our friend, but some things it can never know.
