1. The story: the golem's book of spells

The scroll-writers had a tiresome habit. Whenever the golem had to compute a power, they copied the same twelve lines into the scroll again. One day a copy had a mistake in it, and they had to hunt through the whole scroll for every copy.

So they started a book of spells. Each spell is written once, on its own page, under a name: pow. At the top of the page stands a promise: "Hand me a number and a whole exponent, never zero to a negative power, and I hand you back the power." In the scroll they now only write: cast pow with 2 and −2.

When the golem meets that line, it marks its place, walks to the page, and sets up a fresh little workbench. On it go copies of the two ingredients. Whatever the spell does to them happens to the copies, never to the originals left behind. When the spell says "return", the golem carries back exactly one thing, clears the bench, and continues the scroll where it left off.

In C++: the spell is a function, its name and ingredients are the function name and parameters, the thing carried back is the return value, the workbench is the function's stack frame, the copies are pass by value, and the promise at the top is the pre- and postcondition. The script's motivation (p. 71) is the scroll-writers' problem: copy-and-paste creates redundancy, and "errors once made propagate to lots of places".

2. Defining a function

Function definition (script p. 72–73):

T fname (T1 pname1, T2 pname2, …, Tn pnamen) block

  • T is the return type: the type of the value the function hands back;
  • fname is the name by which it is called;
  • T1 pname1, … are the formal parameters, each with a type and a name usable inside the body;
  • the body is a block, run when the function is called.

Definitions stand one after another, outside of every other function: you cannot define a function inside main, inside a block or inside a loop (p. 73).

The script's first function is the power $b^e$ for a whole exponent, including negative ones: $b^{e} = (1/b)^{-e}$ (Code 6.1, p. 72). Here it is with comments:

#include <iostream>

// PRE:  e >= 0 || b != 0.0
// POST: return value is b^e
double pow(double b, int e) {   // return type double, two parameters
  double result = 1.0;          // accumulator for a product
  if (e < 0) {                  // b^e = (1/b)^(-e)
    b = 1.0 / b;
    e = -e;
  }
  for (int i = 0; i < e; ++i) {
    result *= b;
  }
  return result;                // hand the value back to the caller
}

int main() {
  std::cout << pow( 2.0, -2) << "\n";   // 0.25
  std::cout << pow( 1.5,  2) << "\n";   // 2.25
  std::cout << pow(-2.0,  9) << "\n";   // -512
  return 0;
}

// POST: returns l XOR r (true if exactly one is true)
bool Xor(bool l, bool r) {
  return l != r;

// PRE:  n >= 0
// POST: returns the n-th harmonic number 1 + 1/2 + ... + 1/n,
//       summed backwards (small terms first: less rounding error)
float Harmonic(int n) {
  float res = 0;
  for (int i = n; i >= 1; --i) {
    res += 1.0f / i;
  }
  return res;
}

// POST: returns the minimum of a and b
int min(int a, int b) {
  if (a < b)
    return a;
  else
    return b;
}

Why 1.0f / i and not 1 / i? Lesson 2: two ints divide without remainder, so 1 / i is 0 for every i ≥ 2.

3. Calling a function, and what happens then

Function call (p. 74): fname(expression1, …, expressionN). Every call argument must be convertible to the type of its formal parameter. The call is an expression: its type is the return type, its value is the returned value. So you can use a call anywhere a value of that type fits: x = 2 * pow(a, n) + 1;

For the types we know so far, the arguments and the call itself are R-values (p. 74): the function receives values, not variables.

The script lists five steps (p. 74). Turned into a tracing method, they extend the trace table from the Task method:

A function call in five steps

  1. What are the argument values? Evaluate every argument in the caller, with the caller's current values. (The order in which several arguments are evaluated is not specified; it only matters if one argument changes a variable another reads.)
  2. What is the new table? Start a new table for this call, below the caller's. Its first rows are the parameters, initialised with the values from step 1: b = 2.0, e = -2. The caller's table stays as it is, untouched, until the call is over.
  3. What does the body do? Trace the body in the new table only. Parameters behave like local variables. Names in the new table have nothing to do with equal names in the caller's table.
  4. Which return is reached, with which value? The first return expression; reached ends the call at once, also from inside a loop.
  5. Where does the value go? Cross out the whole new table (the call is over) and write the returned value in place of the call in the caller's expression. Continue there.

Pass by value: the caller's variables are safe

The parameters exist only during the call and only inside the function (p. 75): they are created anew at every call (automatic storage duration) and initialised with copies of the argument values. Changing a parameter therefore never changes a variable of the caller, even one with the same name. The script's Example 6.7 (p. 75):

#include <iostream>

double pow(double b, int e) {   // this b and e are pow's own variables
  double r = 1.0;
  if (e < 0) {
    b = 1.0 / b;                // changes pow's b only
    e = -e;                     // changes pow's e only
  }
  for (int i = 0; i < e; ++i) {
    r *= b;
  }
  return r;
}

int main() {
  double b = 2.0;               // main's b and e: different variables
  int e = -2;
  double z = pow(b, e);         // pow receives the VALUES 2.0 and -2
  std::cout << z << " " << b << " " << e << "\n";
  return 0;
}
0.25 2 -2

In the two-table picture: main's table says b = 2.0, e = -2 the whole time; only pow's table had b = 0.5, e = 2, and it was crossed out at the return.

4. Behind the scenes: the call stack (script 6.4, marked *)

The script marks this section as optional, "not vital, but interesting" (p. 76). It explains why the two-table picture is right, and it prepares recursion (lesson 7) and references (lesson 5). Read it once.

Every running function owns an area of memory, its stack frame, with space for its parameters and local variables. A call puts a new frame on top of the caller's; a return removes it (p. 76–78). Worked example 2: IFMP August 2016, task 1 (b) (official exam, 1 point)

True or false? "Call by value enables functions to change the values of their call arguments."

  1. What exactly does the function receive under call by value?
    Answer

    A copy of the value of each argument, in its own frame. The argument itself (for example the caller's variable) is never reached.

  2. So?
    Answer

    False (official solution: false). The function can change its parameters, but they are copies.

5. void, and "every path must return"

void (p. 78–79) is a type with an empty value range. A void function has only an effect, no value. It needs no return: it ends at the end of its body, or at a return; without a value.

The rule for every other function (p. 79): if the end of the body is reached without a return, the behaviour is undefined. Every execution path must reach a return.

#include <iostream>

// POST: writes the pair "(i, j)" and a line break to std::cout
void print_pair(int i, int j) {            // void: effect only
  std::cout << "(" << i << ", " << j << ")\n";
}                                          // no return needed

int main() {
  print_pair(3, 4);
  return 0;
}
(3, 4)

The script's warning example (p. 79–80), in three versions:

// WRONG: for x far from y, the end of the body is reached
// without a return. compare(10, 20) is undefined.
bool compare(float x, float y) {
  float delta = x - y;
  if (delta * delta < 0.001f) return true;
}

// BETTER: both paths return
bool compare(float x, float y) {
  float delta = x - y;
  if (delta * delta < 0.001f)
    return true;
  else
    return false;
}

// BEST: the condition already is the bool we want
bool compare(float x, float y) {
  float delta = x - y;
  return delta * delta < 0.001f;
}

The compiler accepts the wrong version; with -Wall it warns "control reaches end of non-void function". Treat that warning as an error. And the last version is a pattern to keep: if a function returns a bool, return the condition itself instead of if (c) return true; else return false;.

6. Pre- and postconditions

Precondition (p. 80): what must hold when the function is called. It defines the function's domain.

Postcondition (p. 80): what is guaranteed after the call, provided the precondition held. It states the value (what is returned) and the effect (what is printed, read or changed).

Correctness (p. 81): if the precondition holds at the call, the postcondition holds after it. If the precondition does not hold, the function promises nothing: undefined behaviour.

They are comments: the compiler ignores them. They are written for people, so that a user of the function doesn't need to read its body.

// PRE:  e >= 0 || b != 0.0
// POST: return value is b^e
double pow(double b, int e);

Read the PRE of pow carefully: it excludes exactly the case where the body would divide by zero, $b = 0$ with $e < 0$. (It allows $0^0$, which the loop returns as 1.)

Weak precondition, strong postcondition

The script's question (p. 81): which is more useful, a strong or a weak precondition? A precondition "b = 0 and e = 1" would make pow trivial to write (return 0) and correct, but useless. So:

  • Preconditions as weak as possible: allow the largest possible domain. Exclude only what really breaks the function.
  • Postconditions as strong as possible: say as precisely as you can what comes out. "Returns some number" is correct for every function and says nothing.

The script is honest about the limits (p. 81): pow can overflow or round, which the POST "returns $b^e$" ignores. Specifying every platform limit would be unreadable, so we write mathematical conditions and use common sense: "Do not over-engineer but also do not become careless." In exams, "ignore overflow" is usually said explicitly.

Checking a precondition: assert

With #include <cassert>, the statement assert(expression); does nothing if the expression is true, and stops the program with an error message if it is false (p. 81–82). On Code Expert that is exit code −6 (SIGABRT). Use it to turn a silent wrong answer into a loud stop at the first broken assumption:

#include <cassert>

// PRE:  e >= 0 || b != 0.0
// POST: return value is b^e
double pow(double b, int e) {
  assert(e >= 0 || b != 0.0);   // the PRE, as code
  double result = 1.0;
  // ... as before
}

An assert can also check a postcondition when the result is easy to verify, like a root of a polynomial (script Example 6.15, p. 82): plug it in and assert that the result is (nearly) 0. The script's recommendation (p. 82): use assertions "wherever reasonably possible"; their cost is negligible. (C++ has a gentler tool, exceptions, which this course skips, p. 83.)

Writing PRE and POST in five steps

For the exam question "give a precondition and a postcondition that completely specify the function".

  1. What are the types, and what can come in? List the parameters with their types. Negative values are possible for int, not for unsigned int.
  2. What does it do on small inputs? Trace three or four tiny calls with a table, and write down argument → result.
  3. What is the pattern, in mathematical words? Name it: "$a\cdot b$", "the number of decimal digits of n", "true iff n is a power of 2". That is the POST. Include the effect if there is one (output, input).
  4. Which inputs break it? Look for: division or % by zero, a loop that never stops, a variable read before it gets a value, an index out of range. Excluding exactly those is the PRE. If nothing breaks, write "PRE: none" (or leave the PRE out).
  5. Does the POST hold at the edges of the PRE? Check the smallest allowed input (0, 1, an empty range). If the POST is wrong there, refine it with a case: "…, and 0 if i == 0".

Worked example 3: the prime test as a function (script p. 96)

bool is_prime(int n) {
  int d = 2;
  for (; n % d != 0; ++d);   // search until found (empty body)
  return d == n;
}
  1. Step 2: trace n = 7, n = 9, n = 2.
    Answer

    7: d stops at 7, 7 == 7, true. 9: d stops at 3, false. 2: d = 2 divides at once, 2 == 2, true.

  2. Step 3: POST?
    Answer

    The loop stops at the smallest divisor d ≥ 2 of n, and that equals n exactly when n has no smaller divisor ≥ 2. POST: returns true if and only if n is prime.

  3. Step 4: which n break it? Try n = 1, n = 0, n = −4.
    Answer

    n = 1: 1 % d is 1 for every d ≥ 2, so the loop never finds a divisor; d grows until it overflows (undefined behaviour). n = 0: 0 % 2 == 0, so d = 2 and it returns 2 == 0, false: fine, 0 isn't prime. n = −4: −4 % 2 == 0, returns false: fine. n = −7: the loop stops at d = 7 (−7 % 7 == 0), returns false: fine. Only 1 and −1 never stop. PRE: n != 1 && n != -1, or the simpler and stronger n >= 2, which the script uses with assert(n > 1). Both are correct; the weaker one is more general.

  4. The script then speeds it up: test only up to $\lfloor\sqrt n\rfloor$ (p. 96). Why is that enough?
    Answer

    If $n = a\cdot b$ with $2\le a\le b$, then $a^2 \le ab = n$, so $a\le\sqrt n$: a composite number always has a divisor up to $\sqrt n$. The script adds a subtle point: this relies on std::sqrt rounding correctly (IEEE 754). If $\sqrt{49}$ came out as 6.9999…, the bound would be 6 and 49 would be called prime. That is the standard library's quality guarantee at work (section 9).

7. Stepwise refinement

A technique by Niklaus Wirth, professor at ETH (script p. 83): solve the problem in steps, from coarse to fine. Start with a "solution" of comments and calls to functions that don't exist yet. Then replace each comment by code and implement each function the same way. Two rules make it work:

  • After every step, the program compiles. A function that isn't written yet gets a stub (return false; // todo).
  • Write the PRE and POST of a function before its body (p. 86). Then you know exactly what you're implementing, and the caller can rely on it before it exists.

It is question 3 of the six questions ("no magic steps") with a structure: every magic step becomes a function, and you refine it later.

Coding task 1: do two rectangles overlap? (script Section 6.7, p. 83–89)

Read two rectangles, each as x y w h (lower-left corner, width, height; width and height may be negative, which flips the rectangle), and print overlap! or no overlap!. Touching edges count as overlap.

You'll need these

De Morgan's rules from lesson 2, and functions with a bool return value (section 2).

What the contract forces (before any idea)
  • Given: eight ints, two rectangles $(x,y,w,h)$; widths and heights may be negative.
  • Must hold at the end: exactly one of the lines overlap! or no overlap!, and it is the true one, touching included.
  • The gap to fill: "is there an overlap?" is far too big for one line. Which smaller questions is it made of?

Try it yourself. The stubs below already compile (that is the first step of stepwise refinement). Replace the two return false; // todo lines and press Check.

int main() {
  std::cout << "Enter two rectangles [x y w h each]\n";
  int x1, y1, w1, h1;
  std::cin >> x1 >> y1 >> w1 >> h1;

  1. What goes in, what comes out?
    My answer

    In: eight ints. Out: one of two lines. A model decision (p. 84): a rectangle is $(x, y, w, h)$, covering the x-interval between x and x + w and the y-interval between y and y + h.

  2. Examples by hand. (0, 0, 4, 3) with (2, 1, 5, 5)? (0, 0, 2, 2) with (3, 0, 1, 1)?
    My answer

    Draw them. First: x-intervals [0, 4] and [2, 7] share [2, 4]; y-intervals [0, 3] and [1, 6] share [1, 3]: overlap. Second: x-intervals [0, 2] and [3, 4] are separate: no overlap, whatever y does.

  3. Steps in words: the coarsest version first.
    My answer

    main: input two rectangles; is there an overlap?; output. "Is there an overlap?" is a magic step: make it a function rectangles_overlap, first as a stub returning false, so the program compiles and the input part can already be tested (p. 84–86).

  4. Refine the magic step. When do two rectangles overlap? What smaller question is hiding in it?
    My answer

    From the drawing (p. 86): two rectangles overlap if and only if their x-intervals overlap and their y-intervals overlap. That is a new, smaller function intervals_overlap(a1, b1, a2, b2), called twice. Write its contract first: PRE: $[a, b]$ means $[b, a]$ if $a > b$ (that handles negative widths); POST: true iff the intervals overlap.

  5. Refine again. When do two intervals overlap?
    Hint 1

    The script's trick: ask the negated question. When do two intervals not overlap?

    Hint 2

    With negative widths, an interval's left end is the smaller of its two numbers. Which library function gives you that?

    My answer

    They do not overlap if one lies entirely to the right of the other: $\min(a_1,b_1) > \max(a_2,b_2)$ or $\min(a_2,b_2) > \max(a_1,b_1)$. By De Morgan (lesson 2), they overlap iff $\max(a_1,b_1) \ge \min(a_2,b_2)$ and $\min(a_1,b_1) \le \max(a_2,b_2)$ (p. 87). min and max exist in the standard library: std::min, std::max from <algorithm>. Nothing magic is left.

      && std::min(a1, b1) <= std::max(a2, b2);

// PRE:  [a1, b1], [a2, b2] are (generalized) intervals,
//       with [a, b] := [b, a] if a > b
// POST: returns true if [a1, b1] and [a2, b2] overlap
bool intervals_overlap(int a1, int b1, int a2, int b2) {
  return std::max(a1, b1) >= std::min(a2, b2)
      && std::min(a1, b1) <= std::max(a2, b2);
}

// PRE:  (x1, y1, w1, h1), (x2, y2, w2, h2) are rectangles,
//       where w1, h1, w2, h2 may be negative
// POST: returns true if the two rectangles overlap
bool rectangles_overlap(int x1, int y1, int w1, int h1,
                        int x2, int y2, int w2, int h2) {
  return intervals_overlap(x1, x1 + w1, x2, x2 + w2)    // x-intervals
      && intervals_overlap(y1, y1 + h1, y2, y2 + h2);   // y-intervals
}

int main() {
  // input
  std::cout << "Enter two rectangles [x y w h each]\n";
  int x1, y1, w1, h1;
  std::cin >> x1 >> y1 >> w1 >> h1;
  int x2, y2, w2, h2;
  std::cin >> x2 >> y2 >> w2 >> h2;

  // computation and output
  if (rectangles_overlap(x1, y1, w1, h1, x2, y2, w2, h2))
    std::cout << "overlap!\n";
  else
    std::cout << "no overlap!\n";
  return 0;
}

    Note the order of the definitions: intervals_overlap comes first, because a function can only be called after its declaration (section 8).

8. Where a function can be used: declaration and definition

Scope of a function (p. 88): from its declaration to the end of the file. Calling it earlier is a compiler error, "f was not declared in this scope".

Declaration (p. 89): the signature followed by a semicolon, double pow(double b, int e);. It tells the compiler the function exists, with these types. Definition: signature plus body. A function may be declared many times, but must be defined exactly once.

A forward declaration lets you call a function before its definition. You need one when two functions call each other (script Code 6.4, p. 90), and it lets you put main at the top so the file reads top-down, like stepwise refinement:

#include <iostream>

// forward declarations: the contracts come first
// POST: returns the larger of a and b
int max2(int a, int b);
// POST: returns the largest of a, b and c
int max3(int a, int b, int c);

int main() {
  std::cout << max3(4, 9, 2) << "\n";   // fine: max3 is declared above
  return 0;
}

int max3(int a, int b, int c) {
  return max2(max2(a, b), c);         // one function built on another
}

int max2(int a, int b) {
  if (a > b)
    return a;
  return b;                           // reached only if a <= b
}
9

Without the two declarations, the compiler stops at max3 in main: it reads the file top to bottom and hasn't seen max3 yet.

9. Libraries, header files, namespaces

Functions like pow are useful in many programs. Copying them into each program brings back the copy-and-paste problem, so we put them in a library (p. 90).

Separate compilation and header files

  • Including a source file (#include "mymath.cpp") works like pasting it in (p. 91). Drawbacks: it is recompiled for every program, and it can't be included twice, since a function may be defined only once.
  • Separate compilation (p. 91–93): mymath.cpp is compiled once on its own into an object file. A program that uses pow only needs its declaration; the compiler leaves a gap where the call goes, and the linker later glues the object files into one executable. (The script says you don't need to understand the details.)
  • A header file mymath.h (p. 94) collects the declarations, with their PRE and POST: #include "mymath.h" gives a program every declaration in one line. The definitions stay in mymath.cpp.

This is how Code Expert works. An exercise often comes with a .h file of declarations and contracts, and a .cpp file where you write the bodies; all .cpp files are compiled automatically (script footnote 35, p. 92). So the comments in the .h file are the exact specification your function is tested against.

Namespaces

Big programs and many libraries mean name clashes: two functions called pow. A namespace groups names (p. 94–95): the standard library's are in std, so its power function is std::pow, and the script's own could live in namespace informatik { double pow(double b, int e); } and be called as informatik::pow. The course recommends writing std:: every time and not using namespace std;: you see where each name comes from, and clashes can't go unnoticed (p. 95–96).

The standard library

Use it rather than reinventing it (p. 96): <cmath> (std::sqrt, std::pow, std::abs, …), <algorithm> (std::min, std::max, std::swap, …), <cassert>, <iostream>. Its functions are tested far better than code written from scratch, and documented at cppreference.com. Exception: when an exam task says "don't use the library", it tests that you can write it yourself.

//       x, 0 < x < p such that a * x is congruent to 1 modulo p
unsigned int inverse (unsigned int a, unsigned int p)

  unsigned int x = 1;            // first candidate
  while (a * x % p != 1) {       // (a * x) % p: * and % bind equally, left to right
    x += 1;                      // next candidate
  }
  return x;                      // found: a * x = 1 (mod p)

Worked example 4: IFMP August 2015, task 3 (official exam, 8 points)

The exam's function was written with recursion (lesson 7). Here is a loop that computes exactly the same values, so you can answer all four official questions now:

// PRE:  b > 1
// POST: ?
unsigned int f (unsigned int i, unsigned int b)
{
  unsigned int count = 0;
  while (i > 0) {
    i = i / b;
    ++count;
  }
  return count;
}
  1. (a) What is the postcondition? Use the method: trace f(10, 10), f(999, 10), f(1000, 10), f(0, 10).
    Answer

    2, 3, 4, 0. It counts how often you can divide by b until nothing is left: the number of digits of i in base b. Official POST: returns the number of digits in the base-b representation of i if i > 0, and returns 0 if i == 0. Note the case for 0 (step 5 of the method): "0" has one digit, but f returns 0.

  2. And why is the PRE b > 1?
    Answer

    b = 0: division by zero. b = 1: i / 1 never changes i, so the loop never ends for i > 0.

  3. (b) Output of std::cout << f(10, 2);?
    Answer

    10 = 1010 in binary: 4 digits. Output 4.

  4. (c) Output of std::cout << f(f(65536, 2), 2);?
    Answer

    Inner call first (step 1 of the call method: evaluate arguments). 65536 = $2^{16}$, which is a 1 followed by 16 zeros: 17 binary digits. Then f(17, 2): 17 = 10001, 5 digits. Output 5.

  5. (d) Output of this main? 
    int i = 0;
while (f(++i, 3) <= 2)
  std::cout << i << " ";
    Answer

    ++i increments first, so f sees 1, 2, 3, …. Numbers with at most 2 digits in base 3 are those below $3^2 = 9$. So 1 to 8 are printed; for i = 9 (= 100 in base 3) the condition fails. Output 1 2 3 4 5 6 7 8 (official: 1 2 3 4 5 6 7 8).

  while (x % 2 == 0)
    x /= 2;
  return x == 1;
}
Hint 1

For each function, trace it on 0, a small positive and a negative input. Where does it misbehave (wrong answer, division by zero, endless loop)? That is what the PRE must exclude.

Hint 2

For the POST, trace three or four inputs that are allowed and guess the pattern in words; then check it on one more.

Solution

Frame: the PRE excludes every input where the function misbehaves; the POST says in words what it returns for every input that is left (section 6).

g1. PRE: b >= 0. POST: returns $a\cdot b$. (For b < 0 the loop doesn't run and it returns 0, which is not $a\cdot b$; so the PRE must exclude negative b, or the POST must say "returns a·b if b ≥ 0, else 0".)

g2. PRE: none, every n works. POST: returns the sum of all odd numbers from 1 to n (0 if n < 1). That sum is $\lceil n/2\rceil^2$: 1, 1+3 = 4, 1+3+5 = 9. A complete POST may say either.

g3. PRE: n >= 2. POST: returns the largest divisor of n that is smaller than n (1 if n is prime). Why the PRE: n = 1 makes d = 0 and n % 0 is undefined; n = 0 returns −1, which means nothing; for negative n, d starts below n and runs away from every divisor (an endless loop until overflow). For n ≥ 2 the search stops at the latest at d = 1.

g4. PRE: x > 0 (for x = 0, 0 % 2 == 0 and 0 / 2 == 0: an infinite loop). POST: returns true if and only if x is a power of 2 ($x = 2^k$, $k\ge0$; so 1 counts).

Each function has a bug. Say what goes wrong (1 point) and fix it (1 point). Written by StudyHub.

// POST: returns -1, 0 or 1 for negative, zero, positive x
int sign(int x) {
  if (x > 0) return 1;
  if (x < 0) return -1;
}

// POST: returns the average of a and b
double average(int a, int b) {
  return (a + b) / 2;
}
Solution

Frame: for each function, check the three rules of section 5: every path returns, the types of each operation, and what the caller gets back.

sign: for x = 0 the end of the body is reached without a return: undefined behaviour (section 5), even though it compiles. Fix: add return 0; at the end.

average: (a + b) / 2 is an int division, so average(1, 2) returns 1.0 instead of 1.5. The return type double converts only after the division. Fix: return (a + b) / 2.0;

#include <iostream>

  if (x > 0) return 1;
  if (x < 0) return -1;
  return 0;                  // every path returns now
}

// POST: returns the average of a and b
double average(int a, int b) {
  return (a + b) / 2.0;      // double division
}

int main() {
  std::cout << sign(-5) << " " << sign(0) << " " << average(1, 2) << "\n";

Exercise 4 (declarations) · 2 points

This program doesn't compile. Why, and what are two ways to fix it?

#include <iostream>

int main() {
  std::cout << square(5) << "\n";
  return 0;
}

int square(int x) {
  return x * x;
}
Solution

Frame: a function can be called only below its first declaration (section 8).

The scope of square starts at its first declaration, below main: "‘square’ was not declared in this scope". Fix 1: move the definition above main. Fix 2: add the forward declaration int square(int x); above main.

Exercise 5 (true or false) · 3 points

  1. A function with return type bool may end without a return statement if its result is never used.
  2. The compiler checks that the precondition of a function holds at every call.
  3. A function can be declared several times but defined only once.
Solution

Frame: each statement is about one rule of this lesson; find it, then decide.

1. False: reaching the end of a non-void function is undefined behaviour, used or not (p. 79). 2. False: pre- and postconditions are comments; only an assert checks, and at run time (p. 80–81). 3. True (p. 89).

Summary: what to keep from lesson 4

  • T name(T1 p1, …) { body }. A call is an expression of type T. Functions are defined outside every other function.
  • A call: evaluate the arguments, new table with copies, run the body, the first return ends it, its value replaces the call. Pass by value: the caller's variables never change.
  • void functions need no return; every other function must reach a return on every path.
  • PRE: what must hold at the call (as weak as possible). POST: value and effect afterwards (as strong as possible). assert checks at run time.
  • Stepwise refinement: comments and stubs first, contracts before bodies, compile after every step, test the smallest functions first.
  • A function is usable from its declaration on. Headers hold declarations, .cpp files definitions, the linker joins them. Write std::.
  • Methods: a function call in five steps; PRE and POST in five steps.

For wonder: the ETH professor behind stepwise refinement (optional, 5 min)

Niklaus Wirth, whose 1971 paper "Program Development by Stepwise Refinement" the script cites (p. 83), was a professor at ETH Zurich. He designed the programming language Pascal there (around 1970), taught generations of programmers with it, and later built Modula-2, Oberon, and with his team even the Lilith workstation, hardware included. He received the Turing Award, computer science's highest honour, in 1984. One of his books is called simply Algorithms + Data Structures = Programs. The technique you used for rectangles and calendars was invented a few hundred metres from your lecture hall.
