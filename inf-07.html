1. The story: the spell that casts itself

One page in the book of spells puzzled the apprentices. The spell fac, "the factorial of a number", said: "If the number is 1 or less, hand back 1. Otherwise, cast fac on the number one smaller, and multiply what comes back by the number." The spell used itself.

"That can't work," said one apprentice. "To know fac of 4 you must already know fac of 3." But the golem didn't mind. It set up a workbench for fac 4, reached the line "cast fac on 3", left a note "waiting here", and set up a second bench on top of the first, for fac 3. Then a third for fac 2, a fourth for fac 1. That one needed nothing: "hand back 1". The top bench was cleared, the 1 carried down; fac 2 multiplied and handed down 2, then 6, then 24.

The old scroll-writer added a warning in the margin: "A spell that casts itself must always cast itself on something smaller, and there must be a smallest thing it can answer at once. Otherwise the benches pile up to the ceiling, and the workshop collapses."

In C++: a spell that uses itself is a recursive function, "1 or less" is the base case, "one smaller" is the progress towards it, the pile of benches is the call stack, and the collapse is a stack overflow. Nothing new is needed in the language: a function may call any function that is declared, itself included.

2. Recursive functions: base case and progress

Many mathematical functions are naturally defined recursively, that is, the function appears in its own definition (p. 119). The factorial: $$ n! = \begin{cases} 1, & \text{if } n \le 1\\ (n-1)!\cdot n, & \text{otherwise.}\end{cases}$$ Read it as "if we already know $(n-1)!$, we get $n!$ by one multiplication". In C++ it looks exactly the same (p. 119):

#include <iostream>

// POST: return value is n!
int fac(int n) {
  if (n <= 1) return 1;            // base case
  else return fac(n - 1) * n;      // recursive case: a smaller argument
}

int main() {
  std::cout << fac(4) << " " << fac(10) << "\n";
  return 0;
}
24 3628800

Recursive function (p. 119): a function that calls itself. The simplest one, void f() { f(); }, is useless: it calls itself forever, "as helpful as the definition 'Ein Euro ist ein Euro'" (p. 120), and it burns time and memory until the stack overflows.

What every useful recursion needs (p. 120):

  • at least one base case: a case without a recursive call, where the answer is direct (here n ≤ 1);
  • in every recursive case, a call with an argument that is strictly closer to the base case (here n − 1 instead of n).

Then the base case is reached after finitely many calls, and the recursion ends. So a recursive function always starts with an if that checks for the base case.

This is the same argument as for loops in lesson 3: a loop ends if every round makes progress towards the stop condition. For recursion, the "rounds" are the calls.

Writing a recursive function: four questions

The script asks two questions (p. 124); we add the two checks that make the answer safe.

  1. Which smaller subproblem would make the problem easy, if I already had its solution? For n!: the solution for n − 1. Trust that the recursive call solves it; don't trace it in your head.
  2. When is the problem trivial? That is the base case: n ≤ 1. Return its answer directly.
  3. Does every recursive call move strictly towards the base case? n − 1 < n, and from n ≥ 2 we reach 1. If you can't say why, the recursion may not end.
  4. How do I combine? Use the subproblem's answer to build the full one: fac(n - 1) * n.

3. The call stack

What happens in memory is what lesson 4, section 4 described, with one new twist: the same function is on the stack several times (p. 120–122). Each call gets its own frame with its own argument, its own local variables and the return address (where to continue afterwards). While fac(1) runs, the stack holds $$\texttt{fac(4)} \Rightarrow \texttt{fac(3)} \Rightarrow \texttt{fac(2)} \Rightarrow \texttt{fac(1)},$$ with fac(1) on top. None of them has finished; the lower ones wait for the value of the call above them. "Every function call has its own local arguments" (p. 122): the four n's are four different variables, with values 4, 3, 2, 1.

Worked example 1: the call fac(4) (script Figure 10.1, p. 122)

  1. Which calls are made, in which order, before the first one returns?
    Answer

    fac(4) calls fac(3), which calls fac(2), which calls fac(1). Four frames on the stack.

  2. Fill in the table from the top of the stack down: what does each call return?
    Answer
    callits ncomputesreturns
    fac(1)1base case1
    fac(2)2fac(1) · 2 = 1 · 22
    fac(3)3fac(2) · 3 = 2 · 36
    fac(4)4fac(3) · 4 = 6 · 424

    The calls go up in the order 4, 3, 2, 1; the returns come back down in the order 1, 2, 3, 4.

  3. What happens with fac(100000)?
    Answer

    Two problems. The value overflows int long before (13! already does). And 100 000 frames may not fit on the stack: a stack overflow, undefined behaviour, usually a segmentation fault (p. 126). On Code Expert that shows as exit code −11.

4. Euclid's algorithm, recursively (script 10.2)

Lesson 1 met Euclid's algorithm for the greatest common divisor. It is a mathematical recursion (p. 122): $$\gcd(a, b) = \begin{cases} a, & \text{if } b = 0\\ \gcd(b,\ a \bmod b), & \text{otherwise,}\end{cases}$$ and translates one to one:

#include <iostream>

// PRE:  a, b >= 0, not both 0
// POST: returns the greatest common divisor of a and b
int gcd(int a, int b) {
  if (b == 0) return a;
  else return gcd(b, a % b);
}

int main() {
  std::cout << gcd(48, 18) << " " << gcd(17, 5) << " " << gcd(0, 7) << "\n";
  return 0;
}

5. All bit strings of length n (script 10.3)

Factorial and gcd are just as easy with a loop. Here is a problem where recursion really helps (p. 123): print all bit strings of length n, from 000…0 to 111…1. With loops you'd have to remember, for every position, which bit you tried last. With the four questions:

  1. Subproblem: "all bit strings of length n that start with a given prefix". All strings starting with p are those starting with p + "0", then those starting with p + "1".
  2. Trivial: when the prefix already has length n, there is exactly one such string: the prefix itself. Print it.
  3. Progress: each call makes the prefix one character longer; after n steps it has length n.
  4. Combine: nothing to combine, just do the two calls one after the other.
#include <iostream>
#include <string>

// POST: all bit strings of length n that start with prefix
//       are written to std::cout, one per line, in increasing order
void all_bit_strings(int n, std::string prefix) {
  if (std::ssize(prefix) == n) {
    std::cout << prefix << "\n";                // base case
  } else {
    all_bit_strings(n, prefix + "0");           // first all with a 0 next
    all_bit_strings(n, prefix + "1");           // then all with a 1 next
  }
}

int main() {
  int n;
  std::cin >> n;
  all_bit_strings(n, "");                       // empty prefix: all strings
  return 0;
}

Write bs(p) for all_bit_strings(3, p).

  1. Which calls happen before 001 is printed?
    Answer

    bs("") → bs("0") → bs("00") → bs("000"), which prints 000 and returns. Back in bs("00"), its second call bs("001") prints 001.

  2. How many calls does bs("") make in total, itself included, for n = 3?
    Answer

    One call per node of the tree in Figure 10.2: 1 + 2 + 4 + 8 = 15. In general $2^{n+1} - 1$, of which $2^n$ print.

  3. How many calls are on the stack at most at the same time?
    Answer

    4 for n = 3: bs(""), bs("0"), bs("00"), bs("000"). In general n + 1. That is the recursion depth (section 6).

Each of these frames holds its own copy of the prefix string (Figure 10.4, p. 126). The script's improvement passes one string by reference and an index i, "the left-most to-be-modified bit" (p. 126–127):

void all_bit_strings(std::string& bit_string, int i) {

    bit_string[i] = '1';

6. Two strategies: decrease and conquer, divide and conquer (script 10.5)

The script shows both on a toy problem that a loop solves easily: the sum of a vector (p. 128).

Decrease and conquer: remove a small part (the first element), solve the rest recursively, and combine (p. 128–129). Instead of copying the rest, an index from says where the rest starts:

// POST: returns the sum of v[from], v[from+1], ..., v[size-1]
int sum(const std::vector<int>& v, int from) {
  if (from >= std::ssize(v))
    return 0;                               // empty rest
  else
    return v[from] + sum(v, from + 1);      // first + sum of the rest
}
// call: sum(v, 0)

Divide and conquer: split the problem into two halves, solve both recursively, and combine (p. 129–130):

// POST: returns the sum of v[from], ..., v[to] (0 if from > to)
int sum(const std::vector<int>& v, int from, int to) {
  if (from > to)
    return 0;                               // empty part
  else if (from == to)
    return v.at(from);                      // one element
  else {
    int middle = (from + to) / 2;
    return sum(v, from, middle) + sum(v, middle + 1, to);
  }
}
// call: sum(v, 0, std::ssize(v) - 1)

Recursion depth (p. 131): the largest number of calls active at the same time, that is, the most frames on the stack. Decrease and conquer on n elements reaches depth about n (here n + 1, with the call for the empty rest). Divide and conquer halves each time and reaches depth about $\log_2 n$. Smaller depth means less stack memory, so larger inputs before a stack overflow. Divide and conquer is also easy to run in parallel. "You should know what the recursion depth is and how to determine it for a specific call (for small values)" (p. 131, footnote).

Worked example 4: recursion depth for v = {−1, 4, 6, 7} (script Figures 10.6 and 10.7)

  1. Decrease and conquer, sum(v, 0): which calls are on the stack at the deepest point?
    Answer

    sum(v, 0), sum(v, 1), sum(v, 2), sum(v, 3), sum(v, 4): five, the last one for the empty rest. Depth 5. The results come back as 0, 7, 13, 17, 16.

  2. Divide and conquer, sum(v, 0, 3)?
    Answer

    sum(v, 0, 3) calls sum(v, 0, 1) (middle = 1), which calls sum(v, 0, 0), a base case. Deepest: three calls, depth 3. The two halves give 3 and 13, total 16.

  3. And for a vector of 1024 elements?
    Answer

    Decrease and conquer: 1025. Divide and conquer: 11 (halving 1024 ten times reaches 1 element, plus the first call).

7. Recursion or iteration? The Fibonacci numbers (script 10.6)

The Fibonacci numbers: $F_0 = 0$, $F_1 = 1$, $F_n = F_{n-1} + F_{n-2}$ for n > 1, so 0, 1, 1, 2, 3, 5, 8, 13, 21, … (p. 131). Translated one to one (p. 132):

int fib(int n) {
  if (n == 0) return 0;
  if (n == 1) return 1;
  return fib(n - 1) + fib(n - 2);
}

It is correct, and fib(50) takes "forever" (Example 10.2, p. 132). The reason is in the call tree (Figure 10.9): fib(50) calls fib(49) and fib(48); fib(49) calls fib(48) again, and so on. $F_{48}$ is computed 2 times, $F_{47}$ 3 times, $F_{46}$ 5 times, …, and $F_1$ "around $10^9$ times" (the exact count is $F_{50} \approx 1.3\cdot 10^{10}$): the counts are themselves Fibonacci numbers. The subproblems overlap, and each is solved from scratch every time.

The loop computes every $F_i$ exactly once, in increasing order, and only remembers the last two (p. 133):

#include <iostream>

// POST: returns the n-th Fibonacci number
long long fibonacci(int n) {
  if (n == 0) return 0;
  if (n == 1) return 1;
  long long fib2 = 0;   // value two before
  long long fib1 = 1;   // value one before
  long long fib = 0;    // current value
  for (int i = 2; i <= n; ++i) {
    fib = fib2 + fib1;  // i-th Fibonacci number
    fib2 = fib1;
    fib1 = fib;
  }
  return fib;
}

int main() {
  int n;
  std::cin >> n;
  std::cout << fibonacci(n) << "\n";
  return 0;
}
12586269025

The script uses int; $F_{50}$ is larger than the largest int (about $2.1\cdot 10^9$), so we wrote long long, a 64-bit integer type, to print the right number.

Recursion or iteration? (p. 133). Everything recursive can be written with loops (if necessary with your own stack, for example in a vector), and the other way round. Recursive solutions are often simpler, shorter and more elegant. They are almost always less efficient: every call costs time, overlapping subproblems are solved again and again, and a large depth can overflow the stack. A standard approach is to first find the elegant recursion, then turn it into a loop systematically (dynamic programming, in later courses).

How to write this under exam pressure
  1. Take the loop idea (two indices) and make the indices parameters.
  2. Base case: what the loop's stop condition was (i >= j).
  3. Recursive case: one step of the loop body, then call yourself with the updated indices.
  4. A wrapper with the original signature makes the first call.

In short: "loop condition becomes base case, loop step becomes the call".

Coding task 2: Pascal's triangle (Informatik exam August 2023, as Code Expert Exercise 7, Task 4)

In Pascal's triangle, every row starts and ends with 1, and every other entry is the sum of the two entries above it. Rows and columns are numbered from 0:

    1
   1 1
  1 2 1
 1 3 3 1
1 4 6 4 1

Rows 0 to 4. The 6 in row 4 is 3 + 3 from the two entries above it.

Implement a recursive function that returns the value at (row, col). main reads n and prints the first n rows, one per line.

You'll need these

The four questions (section 2); the entry at (row, col) is the binomial coefficient $\binom{row}{col}$ from Analysis, if you know it.

What the contract forces (before any idea)
  • Given: a valid position, 0 ≤ col ≤ row.
  • Must hold at the end: the value at that position, following the rule "1 at the edges, otherwise the sum of the two above".
  • The gap to fill: which positions are "above" (row − 1, col − 1) and (row − 1, col), and which positions are the edges.

Coding task 3: the largest element, divide and conquer (script Section 10.5, p. 129–131)

Write the maximum of a vector the way the script writes the divide-and-conquer sum: split the part v[from..to] into two halves, find the maximum of each recursively, and combine. main reads n and n numbers (n ≥ 1) and prints the maximum.

You'll need these

The divide-and-conquer sum of section 6, and const std::vector<int>& from lesson 5.

What the contract forces (before any idea)
  • Given: a vector to read, and a non-empty part from ≤ to.
  • Must hold at the end: the largest of v[from], …, v[to] is returned.
  • The gap to fill: the base case (unlike the sum, an empty part has no maximum, so the PRE excludes it), the split, and the combination.

Try it yourself: write the body, then press Check.

#include <iostream>
#include <vector>

// PRE:  0 <= from <= to < std::ssize(v)
// POST: returns the largest of v[from], ..., v[to]
int max_of(const std::vector<int>& v, int from, int to) {
  return v[from]; // todo
}

int main() {
  int n;
  std::cin >> n;
  std::vector<int> v = std::vector<int>(n);

  1. The four questions.
    My answer

    (1) Subproblems: the maxima of the two halves. (2) Trivial: one element (from == to): it is the maximum. (3) Progress: both halves are strictly shorter and never empty, because middle = (from + to) / 2 lies in [from, to). (4) Combine: the larger of the two.

  2. By hand: {3, 9, 2, 7, 4}.
    My answer

    max_of(0, 4): middle 2. Left max_of(0, 2): middle 1, halves (0, 1) → max(3, 9) = 9 and (2, 2) → 2, so 9. Right max_of(3, 4): 7 and 4, so 7. Combined: 9.

  3. Write it.
    Answer (written by StudyHub after the script's sum, checked by compiling)

    Frame: divide and conquer: one element is the base case; otherwise split at the middle and return the larger of the two maxima.

    The golem's stepsWhat you write

    One jar only: its value is the largest.

    if (from == to) return v[from];

    Otherwise, split the row of jars in the middle and ask two fresh benches.

    int middle = (from + to) / 2;

    Keep the larger answer.

    if (left > right) return left;

int max_of(const std::vector<int>& v, int from, int to) {

    My answer

Worked example 5: IFMP August 2015, task 3, the original (official exam, 8 points)

In lesson 4 you solved this task with a loop version of f. Here is the function as the exam really gave it:

// PRE: b > 1
// POST: ?
unsigned int f (unsigned int i, unsigned int b)
{
  if (i == 0) return 0;
  return 1 + f (i/b, b);
}
  1. Base case and progress?
    Answer

    Base case i == 0, answer 0. Progress: i/b < i for i > 0 and b > 1, so i reaches 0. That is also why the PRE says b > 1: for b = 1, i/1 = i and the recursion never ends.

  2. Trace f(10, 2) as a stack of calls.
    Answer

    f(10) = 1 + f(5) = 1 + 1 + f(2) = 1 + 1 + 1 + f(1) = 1 + 1 + 1 + 1 + f(0) = 4. Each call adds 1 per division: f counts how often you can divide by b until 0 is left, which is the number of base-b digits. Official POST: "returns the number of digits in the base-b representation of i if i > 0, and returns 0 if i == 0". Output (b) 4, (c) 5, (d) 1 2 3 4 5 6 7 8, exactly as in lesson 4: the loop and the recursion compute the same function.

  3. The general lesson?
    Answer

    A recursion of the form "if (base) return c; return 1 + f(smaller)" counts the calls until the base case. "return x * f(smaller)" multiplies, "return f(a) + f(b)" adds up a tree. Recognising the shape gives you the POST quickly.

Worked example 6: how many calls does fib(5) make? (script Example 10.2, p. 132)

  1. Draw the call tree of fib(5) level by level and count.
    Answer

    fib(5) → fib(4), fib(3). fib(4) → fib(3), fib(2). Each fib(3) → fib(2), fib(1). Each fib(2) → fib(1), fib(0). Count with $c(n) = 1 + c(n-1) + c(n-2)$ and $c(0) = c(1) = 1$:

    n012345
    calls c(n)1135915

    15 calls to compute the number 5. c(n) grows like the Fibonacci numbers themselves, so c(50) is about $4\cdot 10^{10}$.

  2. Recursion depth of fib(5)?
    Answer

    5: fib(5), fib(4), fib(3), fib(2), fib(1) along the leftmost path. Depth and number of calls are different things: small depth, many calls.

unsigned int g (unsigned int n) {

Exercise 5 (true or false) · 3 points

  1. Every recursive function can be rewritten with loops.
  2. The recursion depth of fac(n) from section 2 is n (for n ≥ 1).
  3. The divide-and-conquer sum of section 6 makes fewer calls in total than the decrease-and-conquer sum.
Solution

Frame: each statement is about sections 6 and 7: depth counts calls on the stack at the same time; the total counts all calls.

1. True (p. 133), if necessary with your own stack. 2. True: fac(n), fac(n − 1), …, fac(1) are on the stack together. 3. False: for n elements, decrease and conquer makes n + 1 calls, divide and conquer about 2n − 1 (one per node of the halving tree). Divide and conquer wins in depth, not in the number of calls.

Summary: what to keep from lesson 7

  • A recursive function calls itself. It needs a base case and, in every recursive case, progress towards it. Otherwise: infinite recursion, stack overflow.
  • Every call has its own frame on the call stack: its own parameters and locals. Calls go up, results come back down.
  • Four questions: which subproblem; when trivial; why progress; how to combine. Trust the recursive call.
  • Prefix recursion generates all bit strings (and all strings with a rule). Pass a string by reference to save memory.
  • Decrease and conquer: one element less, depth about n. Divide and conquer: two halves, depth about $\log_2 n$.
  • Overlapping subproblems (Fibonacci, Pascal) make naive recursion slow; a loop that computes each value once is fast.
  • For the exam: trace small cases in a table, recognise the shape ("1 + f", "x * f", "f + f"), and write the POST in words.

For wonder: the towers of Hanoi (optional, 5 min)

The script lists the towers of Hanoi among the problems with an elegant recursive solution (p. 128). There are three pegs, and n discs of different sizes on the first, the largest at the bottom. Move them all to the third peg, one disc at a time, never putting a larger disc on a smaller one. With the four questions it solves itself: to move n discs from A to C, move the top n − 1 from A to B (recursively), move the largest from A to C, and move the n − 1 from B to C (recursively). That needs $2^n - 1$ moves, and no solution needs fewer. The puzzle was sold in 1883 by the French mathematician Édouard Lucas, with a legend about monks in a temple moving 64 golden discs: when they finish, the world ends. At one move per second, $2^{64} - 1$ moves take about 585 billion years, roughly 40 times the age of the universe.
