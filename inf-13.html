1. The story: the golem returns what it borrows

Every new wagon the golem made in lesson 12 was built from material it borrowed from the store room. The golem never brought anything back. For a short job that didn't matter. But the workshop now runs day and night, and one morning the store room is empty: a leak.

So the store keeper gives the golem a rule: "For everything you take, bring it back, exactly once." Bring nothing back, and the store runs dry. Bring the same plank back twice, and the store keeper's books are wrong. Keep using a plank after you have returned it, and you are working with something that now belongs to someone else.

The golem also learns that when a box is thrown away, its contents must be returned first, and that when it copies a box, it must copy the contents, not just the label that says where they are.

In C++: taking is new, returning is delete (p. 200). "Exactly once" is the guideline of this chapter. The box thrown away is an object whose lifetime ends: its destructor returns the contents. Copying the contents and not the label is a deep copy.

2. A stack, and a delete for every new (script 17.1–17.2)

A stack is a linked list that only allows inserting and removing at the front, the top, like a stack of books (p. 197). Its nodes are the lnodes of lesson 12, and the stack holds a pointer topn to the top node (p. 198):

class stack {
public:
  stack() : topn(nullptr) {}                // default constructor: empty stack
  bool empty() const { return topn == nullptr; }
  int top() const { assert(!empty()); return topn->value; }
  void push(int value) { topn = new lnode(value, topn); }
  void pop();                               // PRE: non-empty stack
private:
  lnode* topn;
};

Our own default constructor matters: the automatically generated one would leave topn uninitialised, not nullptr (p. 198). The first try at pop simply moves topn down one node (p. 199): topn = topn->next;. From the stack's point of view, the top element is gone. But the node itself still exists, and nothing points to it any more.

new and delete (p. 200). Objects made with new live on the heap and have a dynamic lifetime: they live until they are deleted explicitly, unlike local variables, which die at the end of their scope. delete p;, for a pointer p that came from new, destroys the object and frees its memory.

Guideline: for each new, there has to be a matching delete.

  • No delete: a memory leak. The heap fills with unused objects until memory runs out.
  • Using a pointer after its object was deleted: a dangling pointer. delete s; does not set s to nullptr; s and every other pointer to the object still hold the old address. Dereferencing them is undefined behaviour.
  • Deleting the same object twice, for example through two pointers to it: also undefined behaviour (p. 201).
rational* t = new rational(1, 2);
rational* s = t;     // two pointers, one object
delete s;            // object gone; s and t now both dangle
int x = t->d;        // undefined behaviour: dangling pointer
delete t;            // undefined behaviour: deleted twice

The node made in push is removed in pop, so pop gets the matching delete (p. 201). The old top must be remembered first, or after topn = topn->next nothing would point to it any more and it could never be deleted:

void stack::pop() {
  assert(!empty());
  lnode* old_topn = topn;    // remember the top node
  topn = topn->next;         // the stack now starts one lower
  delete old_topn;           // give the old node back
}

3. Destructors (script 17.3)

Now push and pop match. But (p. 201–202):

{
  stack s;
  s.push(1);
  s.push(2);
  s.push(3);
}   // s dies here, its three nodes don't

s is a local variable: at the closing brace it is destroyed, and with it its member topn. The three nodes stay on the heap as "zombies" that nothing points to: a leak again. When a stack dies, its nodes must be deleted too.

The destructor of a class T is the unique member function ~T(); (p. 202). It is called automatically when an object's lifetime ends: at the end of the scope of a local variable, or by delete on a pointer to it. If you declare none, the generated destructor destroys each member, which for an int or a pointer does nothing. So a class that owns heap memory needs its own:

// POST: the dynamic memory of *this is deleted
stack::~stack() {
  while (topn != nullptr) {
    lnode* old_topn = topn;
    topn = topn->next;
    delete old_topn;
  }
}

It is pop, repeated until the stack is empty.

When exactly do destructors run? This small program prints a line in each constructor and destructor:

#include <iostream>

struct noisy {
  char c;
  noisy(char x) : c(x) { std::cout << "make " << c << "\n"; }
  ~noisy() { std::cout << "destroy " << c << "\n"; }
};

int main() {
  noisy a('a');
  {
    noisy b('b');
    noisy* p = new noisy('p');
    noisy c('c');

Worked example 2: reading the noisy output

  1. Why is p destroyed before c, although c was made later?
    Answer

    The object behind p dies exactly at delete p;, which comes before the closing brace. Local variables die at the end of their scope.

  2. In which order do the local variables b and c die?
    Answer

    In reverse order of their declaration: c, then b (the script mentions this on p. 204). Like a stack: the last made is the first destroyed.

  3. If we removed delete p;, what would change in the output?
    Answer

    "destroy p" would never be printed, not even at the end of main. The pointer p dies at the brace, the object it points to doesn't: a leak.

4. Copies: the copy constructor (script 17.4–17.5)

With pop and the destructor, the stack seems safe. But look at this (Code 17.2, p. 204):

{
  stack s1;
  s1.push(1);
  stack s2 = s1;
}

stack s2 = s1; looks harmless. The generated copy makes a member-wise copy: it copies topn, the address, not the nodes (p. 203). Now s1 and s2 share the same node. At the brace, s2's destructor deletes it; then s1's destructor deletes it again, through a dangling pointer: undefined behaviour. In Code 17.1 the same sharing makes s1.pop() delete a node that s2 still uses.

There are three ways out (p. 204): make a real copy of all the data (a deep copy); forbid copies altogether; or share the data deliberately (section 6).

The copy constructor of a class T is the unique constructor T(const T& t) (p. 205). It runs whenever a T is initialised with a T: T x = t; or T x(t);, and also when a T is passed or returned by value. The generated one copies member by member; for a deep copy we write our own:

// POST: *this is initialized with a copy of s
stack::stack(const stack& s) : topn(nullptr) {
  if (s.topn == nullptr) return;
  topn = new lnode(s.topn->value, nullptr);
  lnode* last = topn;
  for (lnode* n = s.topn->next; n != nullptr; n = n->next) {
    lnode* copy = new lnode(n->value, nullptr);
    last->next = copy;
    last = copy;
  }
}

This is the train of lesson 12 again: walk the nodes of s, make a new node for each, and clip it on behind last. The empty stack is a separate case, as in push_back.

5. Assignment and the rule of three (script 17.6–17.7)

Now change stack s2 = s1; to s2 = s1; for a stack s2 that already exists. That is not a construction but an assignment, and it calls a different function: T& T::operator=(const T& t), which returns a reference to its left side by convention (p. 206). The generated one again assigns member by member: s2.topn = s1.topn, shared nodes, and s2's old nodes are leaked as well.

Our own assignment does almost what the copy constructor does, with three differences (p. 206): the left side already exists (no initialisation); its old nodes must be cleaned up first; and self assignment s = s must do nothing. That last one is not a detail: cleaning up first would delete the very nodes we are about to copy. Two helpers from the copy constructor and the destructor (p. 207) make it short:

// POST: *this (left operand) becomes a copy of s (right operand)
stack& stack::operator=(const stack& s) {
  if (this != &s) {          // no self assignment
    clean_up_nodes();        // clean up old data
    topn = s.copy_nodes();   // copy data from s
  }
  return *this;              // convention
}

this != &s compares addresses: is the right side the very same object as the left? Never call the destructor ~stack() here instead of clean_up_nodes: after a destructor call the object is invalid (p. 208).

Copy-and-swap (p. 208–209), a second way, reuses the copy constructor and the destructor instead of their code:

stack& stack::operator=(const stack& s) {
  if (this != &s) {
    stack copy = s;                // copy constructor
    std::swap(topn, copy.topn);    // copy now has old data of *this
  }                                // destructor of copy cleans up the old data
  return *this;
}

The rule of three, as a checklist

Rule of three (p. 209): if a class declares one of destructor, copy constructor and assignment operator, it should declare all three. In practice: as soon as a class owns heap memory, ask four questions.

  1. Where is each new deleted? Find the matching delete for every new: in pop, in the destructor, in the assignment.
  2. Destructor? When the object dies, are all its nodes deleted?
  3. Copy constructor? Does T b = a; copy the nodes (deep), or is copying forbidden with T(const T&) = delete;?
  4. Assignment? Self assignment checked, old data cleaned up, deep copy made, *this returned; or forbidden with = delete.

Forbidding (p. 209–210) is the second way out of section 4: stack(const stack& s) = delete; and stack& operator=(const stack& s) = delete; make every copy a compiler error. That delete has nothing to do with delete p. The destructor can't be deleted.

6. Shared pointers and garbage collection (script 17.8–17.9)

Smart pointers do the memory management for you (p. 210). A std::shared_ptr<T> (from <memory>) counts how many shared pointers point to its object, and deletes the object when the count reaches 0. Make one with std::make_shared<T>(constructor arguments); use it like a pointer, with * and ->; ask for the count with use_count(). (A std::unique_ptr is the sole owner of its object; the script doesn't go further.)

#include <iostream>
#include <memory>

struct rational {
  int n, d;
  rational(int num, int den) : n(num), d(den) {}
  ~rational() { std::cout << "rational deleted\n"; }
};

int main() {
  std::shared_ptr<rational> sp1 = std::make_shared<rational>(3, 4);
  {
    std::shared_ptr<rational> sp2 = sp1;
    std::cout << sp2->n << " / " << sp2->d << "\n";   // 3 / 4
    {
      std::shared_ptr<rational> sp3 = sp2;
      std::cout << sp1.use_count() << "\n";           // 3
    } // sp3 goes out of scope here; counter is decreased
    sp1 = nullptr; // explicitly remove pointer sp1 to object
    std::cout << sp2.use_count() << "\n";             // 1
  } // sp2 goes out of scope here, rational is deleted
  std::cout << "end of main\n";
  return 0;
}

The script's workshop example (p. 211–215) shows why this matters: workers share tools stored in a map. With tools stored by value, every worker gets its own copy, and the program prints "hammer gets returned!" four times. With raw pointers, nobody is responsible for returning the tool: a leak. With std::shared_ptr<tool>, the hammer is returned exactly once, when its last user lets go.

Garbage collection (p. 215): languages such as Java have a garbage collector that cleans up unused objects on its own. The price: it runs at moments you don't control, and memory is freed late. C++ leaves the control to you, which makes it suitable for time- and memory-critical programs, and is why this chapter exists.

Coding task 1: pop and the destructor (script p. 201–202)

Complete pop, so that the removed node is deleted, and the destructor ~stack, so that a dying stack deletes all its nodes. The program reads commands push x, pop and top (which prints the top value), then prints how many nodes are alive inside the block and after it.

You'll need these

delete and the remembered pointer (section 2), destructors (section 3).

What the contract forces (before any idea)
  • Given: pop: a non-empty stack. Destructor: a stack in any state.
  • Must hold at the end: pop: the top element is gone and its node deleted. Destructor: no node of the stack is left.
  • The gap to fill: keeping hold of a node long enough to delete it.

  1. What should "alive" be after the block, and why does it test the destructor?
    My answer

    0. Inside the block, alive counts the nodes still on the stack. At the closing brace, s dies and its destructor runs; only if it deletes every node does alive drop to 0.

  2. Why can't pop just say delete topn; topn = topn->next;?
    My answer

    After delete topn, topn dangles, and topn->next reads from a deleted node: undefined behaviour. Read next first, so remember the node in a second pointer.

  3. Could the destructor call pop?
    My answer

    Yes: while (!empty()) pop(); is correct and short. The script writes the three lines out; both are fine.

Patterns used: remember, unlink, delete destructor deletes all nodes

How to write this under exam pressure
  1. Before you move a pointer away from a node, ask: who still points to it? If nobody, remember it and delete it.
  2. Read next, then delete; never the other way round.
  3. A class with new in it gets a destructor.

In short: "remember, unlink, delete".

Coding task 2: a deep copy (script p. 203–205)

Write the copy constructor, so that stack s2 = s1; makes s2 an independent copy: same values, same order, its own nodes. The program copies, pops from s1, pushes 99 onto s2 and prints both. With the generated copy, s2 would share s1's nodes, and the program would read a deleted node.

You'll need these

The copy constructor (section 4), and the train of lesson 12, coding task 1, which appends behind a pointer last.

What the contract forces (before any idea)
  • Given: a stack s in any state, possibly empty; topn is already nullptr from the initialiser list.
  • Must hold at the end: *this holds new nodes with the same values in the same order; s is unchanged.
  • The gap to fill: walking s from the top while building the copy from the top, so the order stays.

Try it yourself: write the body, then press Check.

Worked example 4: forbidden copies (script p. 210)

class stack {
public:
  stack();
  ~stack();
  stack(const stack& s) = delete;
  stack& operator=(const stack& s) = delete;
  ...
};
  1. Which of these lines compile: stack s1;, stack s2 = s1;, stack s3; s3 = s1;, void f(stack s); called as f(s1);?
    Answer

    Only stack s1; (and declaring s3). stack s2 = s1; and s3 = s1; are errors ("use of deleted function"). f(s1) too: passing by value copies. A function that needs a stack must take stack& or const stack&.

Exercise 1 (Informatik exam summer 2019, task 8, old exam) · 6 points (our split)

#include <iostream>
#include <vector>

using vector = std::vector<int*>;
using iterator = std::vector<int*>::iterator;

int main () {
  int* a = new int (1);
  int* b = new int (2);
  vector v = {a,a,b};
  *v[1] = 3;
  for (iterator it = v.begin(); it != v.end(); ++it){
    std::cout << *(*it) << " ";
  }
}

(a) What is the output? (2 points) (b) The same integer is meant to be reachable from several places of the vector. What is the problem of this program? (1 point) (c) Someone suggests calling release_vec(v) at the end of main, with

void release_vec(std::vector<int*> v){
  for (iterator it = v.begin(); it != v.end(); ++it){
    delete *it;
  }
}

What is the problem now? (1 point) (d) The exam then shows a class SharedInteger with members int* shared; and unsigned* count;: the constructor makes both with new (count 1), the copy constructor copies both pointers and does ++(*count), the destructor does if (--(*count) == 0) { delete count; delete shared; }, and the assignment uses copy-and-swap. Briefly explain how this shared pointer works. (2 points)

Solution

Frame: count the news and the deletes for each object; two pointers to one object is where trouble starts.

(a) 3 3 2: v[0] and v[1] are both a, so setting *v[1] to 3 changes what v[0] shows too. (b) A memory leak: the two ints made with new are never deleted. (c) a is deleted twice (v[0] and v[1] hold the same address): undefined behaviour. (d) All copies of a SharedInteger share one int and one counter. Each copy adds 1 to the counter; each destructor subtracts 1; the one that brings it to 0 is the last user and deletes the int and the counter. So the int is deleted exactly once, when nobody uses it any more: what std::shared_ptr does (section 6).

Exercise 2 (spot the error, after script p. 200–201) · 3 points

Name the error in each fragment: leak, dangling pointer, or double delete. (1 point each)

// (a)
int* p = new int(5);
p = new int(6);
delete p;
// (b)
int* q = new int(5);

Solution

Frame: for every new, find its delete; then check nothing is used after it.

Summary: what to keep from lesson 13

  • For each new, exactly one delete. None: a leak. Used after delete: a dangling pointer. Twice: undefined behaviour. delete doesn't reset the pointer.
  • pop: remember the node, unlink it, delete it, in that order.
  • Destructor ~T(): runs at the end of a scope or on delete; a class owning nodes deletes them all there.
  • Copies: the generated copy constructor and assignment copy the pointer (shared nodes, later double delete). Write a deep copy: T(const T&), and T& operator=(const T&) with self check, clean-up, copy, return *this; or forbid both with = delete.
  • Rule of three: destructor, copy constructor, assignment: all three or none.
  • Shared pointers: std::make_shared, use_count(); the object is deleted when the last shared pointer lets go.

For wonder: a whole language built on this chapter (optional, 5 min)

Memory errors of exactly the kinds in this lesson (use after delete, double delete, leaks) are behind a large share of serious security holes in browsers and operating systems: Microsoft and Google have both reported that roughly 70 % of their severe security bugs were memory-safety bugs. One answer is garbage collection, as in Java (section 6). Another is the language Rust, first released in 2015: every value has exactly one owner, as with a std::unique_ptr, and the compiler checks, before the program ever runs, that nothing is used after its owner is gone and nothing is freed twice. It is the rule of this chapter, "for each new, exactly one delete", turned into a law the compiler enforces. In C++, you enforce it yourself, with destructors, the rule of three, and smart pointers.
