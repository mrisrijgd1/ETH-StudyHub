A. Writing a program: the six questions

A programming task is two tasks: find an algorithm, then write it in C++. Finish the first before you start the second. Questions 1–4 are the algorithm, 5 is the C++, 6 is the check.

  1. What goes in, what comes out? One line: the input (types, ranges, preconditions), the output (exact format, every space and line break), and any restriction ("only additions", "no if"). In Code Expert, the comments in the starter files are part of this contract.
  2. Can I solve two or three examples by hand? Small numbers, on paper. Watch how you do it. Shrink the problem on purpose: for overflow, pretend int has 4 bits; for a vector, use 3 elements.
  3. What were my steps? Plain words or pseudo-code. Find every magic step (obvious to you, but not one C++ operation, like "round to nearest" or "find the largest") and refine it until there are none.
  4. Does my plan survive another example, including an edge case? Run the plan, not code, on: 0, 1, a negative number, the smallest and largest allowed input, an empty input, all-equal values. Hidden tests love these.
  5. Which pattern do I know that does this? Start from the frame read input · compute · print output. Then match parts of the plan to patterns you know (below). For each pattern you already know the C++; you only fit the pieces together.
  6. How do I know it works? Run the task's examples, then your own: ordinary, boundary, the edge case from question 4, and one large input. Check the exact output format. A passing test is evidence, not proof: be able to say why each line is right.

B. Reading a program: the trace table

Every "What does this print?" and "What is x at the end?" question is answered the same way: be the golem, with a table. From the Guides' chapter "Tracing":

  1. One row per variable, one line for the output. Create the row when the variable is declared; leave its value empty until it gets one.
  2. Assignment: evaluate the right side with the current values, then cross out the old value and write the new one next to it. Never erase: the crossed-out history is how you find mistakes.
  3. Output: append exactly what is printed. << adds no spaces and no line breaks.
  4. Stop signs: a name with no row (compiler error), an empty value being read (undefined behavior), a division by zero, a value leaving the range of its type.
  5. Expressions: use the five steps of lesson 2 for type and value.

Function calls (lesson 4): a new table for every call, starting with the parameters as copies of the argument values; cross it out at the return and write the returned value in place of the call.

Check a trace with C++ Tutor (pythontutor.com, language C++): step forward and compare its "Stack" with your table. Loops, function calls and recursion extend the table; each lesson shows how when it gets there.

C. Testing: the cases the visible tests don't show

From the Guides: the visible tests are examples, not the specification. Before you submit, try deliberately:

  • size: empty, minimal (one element), maximal, all elements equal;
  • values: 0, negative, duplicates, already sorted, reverse sorted;
  • precision and range: the first input where an int would overflow, or where floating point rounding matters;
  • speed: an input large enough to show a slow algorithm or a loop that never ends.

For every surprise: write down the input, what you saw, your guess why, and what fixed it. Never "fix" a failure by special-casing one test.

D. When it doesn't work

  1. Compiler error: read the first message only, at the line it names (or the line just above it). Fix it, compile again. Later messages are often consequences of the first.
  2. Wrong output: find the smallest input that shows it, trace it by hand, and find the first line where the table differs from what you expected.
  3. Crash or no result: the exit code tells you what kind (Guides, "Debugging"). On Code Expert:

E. Using an AI the way the course asks

The exam is without AI. The course's guide allows AI for the exercises as a learning companion, not as the solver. Its workflow, in short:

  1. Try first: contract, examples, a plan (questions 1–4 above).
  2. Ask for guidance, not a solution: "Ask me questions that help me design an algorithm", "Here is my plan; which cases am I missing?", "Explain this compiler error; don't write the code".
  3. Type and adapt the code yourself, and be able to explain every line.
  4. Afterwards, close the chat and redo a small related problem or trace from memory. That is the real exam check.
