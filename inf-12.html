1. The story: the golem builds a train

The golem wants to build a train. Each wagon carries a number plate and a coupling at the back. The first idea: each wagon contains the next wagon. But then that wagon contains the next one, which contains the next, without end: no wagon could ever be finished.

The second idea: each wagon is welded to the next one when it is made. But the golem wants to make the first wagon now and attach more later, and a weld can't wait and can't be moved.

The third idea works: each wagon has a coupling hook that can hang free, or be clipped to any other wagon, and unclipped and clipped again. The golem also learns to make new wagons whenever it likes, in the middle of the work, not just the ones it planned at the start.

In C++: "contains a wagon" is a member of type wagon (doesn't compile); "welded" is a reference wagon& (must be bound at once, can't change); the coupling hook is a pointer wagon*, which can point nowhere (nullptr) and can be changed. Making wagons during the run is dynamic memory: new wagon(4) (p. 178–186).

2. Pointers (script 15.1)

For a type T, T* is the type pointer to T. Its value is the address of an object of type T (p. 179–180). Three operators belong together (p. 180–181):

  • &x, the address operator: the address of the object x; type T*.
  • *p, the dereference operator: the object at the address in p; type T, and an l-value, so you can assign to it.
  • nullptr, the null pointer: points to no object. Dereferencing it is undefined behaviour, usually a crash (p. 182).

A pointer to T must point to a T: std::string* q = p; with int* p is a compiler error (p. 180). The mnemonic of p. 182: read T *p as "*p is a T". In a declaration T *a, *b, each name needs its own star.

Note the two meanings of & and *: in a declaration, int& r is a reference and int* p a pointer; in an expression, &x takes an address and *p dereferences.

#include <iostream>

int main() {
  int x = 5;
  int* p = &x;       // p points to x
  int y = *p;        // y = 5, a copy
  *p = 8;            // changes x through p
  std::cout << x << " " << y << "\n";
  int z = 1;
  p = &z;            // unlike a reference, a pointer can be redirected
  *p += 10;
  std::cout << x << " " << z << "\n";
  int* q = nullptr;  // explicitly points nowhere
  if (q == nullptr)
    std::cout << "q points into the void\n";
  return 0;
}

Pointers to classes and the arrow (p. 182–183). For rational* p = &r; the members of r are (*p).n and (*p).d. The brackets matter: *p.n means *(p.n), and a pointer has no members. Because this is so frequent, there is a shorthand: p->n is (*p).n. Now you also know what this is (lesson 10): a pointer to the object the member function was called on, so this->n is its member n.

The wagons with pointers (Examples 15.10 and 15.11):

#include <iostream>

struct wagon {
  int id;
  wagon* next;
  // initially no wagon is appended
  wagon(int i) : id(i), next(nullptr) {}
};

int main() {
  wagon w1 = wagon(1);
  wagon w2 = wagon(2);
  wagon w3 = wagon(3);
  w1.next = &w2;
  w2.next = &w3;
  std::cout << w1.next->next->id << "\n";   // outputs 3
  return 0;
}
3

Read w1.next->next->id left to right: w1's hook leads to w2, w2's hook leads to w3, and w3's id is 3. w1 itself is an object (a dot), every hook is a pointer (an arrow).

Const and pointers (p. 184–185). Two rules: const T is the same as T const; and a declaration is read from right to left:

declarationread right to leftwhat is protected
int const p1p1 is a constant intp1
int const* p2p2 is a pointer to a constant intthe int (read-only pointer)
int* const p3p3 is a constant pointer to an intthe pointer (can't be redirected)
int const* const p4p4 is a constant pointer to a constant intboth

So in void print(const wagon* w), the wagon is protected; the function can still change its own copy of the pointer, which doesn't affect the caller (p. 185). And const is a promise of the pointer, not of the object: through another, non-const pointer to the same int, the int can change (Example 15.16).

3. Dynamic memory with new (script 15.2)

With n variables of type wagon you have n wagons. To make more while the program runs, you allocate memory yourself (p. 185–186):

new T(...) creates a new object of type T, initialises it with the matching constructor, and returns its address, of type T*. The object lives until it is explicitly deleted: unlike every object so far, it is not released when the pointer to it goes out of scope. (Every new needs a matching delete; that is lesson 13.)

Example 15.18, arbitrarily many wagons. The pointer last always points to the last wagon, so a new one can be clipped on directly:

#include <cassert>
#include <iostream>

struct wagon {
  int id;
  wagon* next;
  wagon(int i) : id(i), next(nullptr) {}
};

int main() {
  int n;                 // number of wagons
  std::cin >> n;
  assert(n >= 1);
  wagon first = wagon(1);
  wagon* last = &first;
  for (int i = 2; i <= n; ++i) {
    wagon* new_wagon = new wagon(i);
    last->next = new_wagon;
    last = new_wagon;
  }
  std::cout << first.next->id << "\n";         // outputs 2
  std::cout << first.next->next->id << "\n";   // outputs 3
  return 0;
}

4. Linked lists (script 16.1)

Remove one brick from the middle of a Lego wall, and every brick after it must move (p. 187). A chain of clipped elements doesn't have that problem. A linked list needs no contiguous memory, inserting and deleting are simple and fast, but there is no fast random access (p. 188). std::list is built this way. The train was a linked list already; now each element is called a node:

struct lnode {
  int value;     // user data
  lnode* next;   // next element pointer
  // Constructor accepting a value and a pointer to the next element
  lnode(int v, lnode* n) : value(v), next(n) {}
};

class our_list {
  lnode* head;   // pointer to the first element of the list
public:
  void print() const;
  int size() const;
  void push_front(int element);
  void push_back(int element);
  ...
};

The list itself is just a pointer to its first node, wrapped in a class (lesson 10): the user sees the interface, not the nodes (p. 189). An empty list has head == nullptr; the last node has next == nullptr.

Walking the list (p. 189–190): n starts at head; while n isn't the null pointer, use n->value, then move to n->next.

// post: output element values of the linked list
void our_list::print() const {
  for (lnode* n = head; n != nullptr; n = n->next)
    std::cout << n->value << ' ';
}

Every list function is a variation of this loop: size counts (p. 193), operator[](i) takes i steps and returns n->value (p. 190; with too large an i, n becomes nullptr and the access is undefined behaviour).

push_front is one line (p. 190):

void our_list::push_front(int e) {
  head = new lnode(e, head);
}

Read it inside out: the new node gets value e and, as its next, the old head; then head points to the new node. It works for the empty list too (the new node's next is nullptr). The node must come from new: a local lnode would disappear when push_front ends, and the list would point into nothing (Remark 16.1).

Linked-list code in four questions

  1. Draw it. Boxes for the nodes, arrows for the pointers, head on the left, a cross for nullptr. Draw before and after.
  2. Which loop? Visit every node: for (lnode* n = head; n != nullptr; n = n->next). Stop at the last node (to append): n->next != nullptr.
  3. Which pointer changes? Name exactly the one or two pointers that get a new value (head, or some n->next), and assign them in an order that loses nothing.
  4. The edge cases? The empty list (head == nullptr), a list of one node, the first and the last position. Every n-> needs n != nullptr.

Worked example 2: push_front step by step

The list is head → 1 → 5 → 6. We call push_front(4) (p. 190).

  1. What does new lnode(4, head) create, before the assignment?
    Answer

    A node with value 4 whose next points to the node 1, the node head points to. For a moment two pointers lead to node 1: head and the new node's next.

  2. And after head = …?
    Answer

    head → 4 → 1 → 5 → 6. Nothing was moved; one node was made and one pointer changed.

  3. The constructor our_list(int size) calls push_front(0) size times, starting with head = nullptr (p. 191). What does our_list(3).print() output, and how do the pointers look?
    Answer

    0 0 0. head → 0 → 0 → 0 → nullptr; the node made first is now the last.

push_back is where the pitfalls are (p. 191–192). The first try walks to the last node and clips a new one on:

void our_list::push_back(int e) {       // buggy (Example 16.2)
  lnode* n = head;                                // list start
  for (; n->next != nullptr; n = n->next);        // run to the end
  n->next = new lnode(e, nullptr);                // append the new element
}

For the empty list, head is nullptr, and already the first n->next is undefined behaviour. The fix is the empty case first; that is coding task 2. The script's lesson from it: in dynamic data structures, take all cases into account. (Example 16.4 has a shorter version with a pointer to a pointer, lnode**. The script shows it as a curiosity and says clearly that it is not good code: "Trying to be clever is very often particularly unclever in programming.")

Faster variants (p. 192–193): push_back walks the whole list every time. A second member tail pointing to the last node makes it immediate, like last in the train; a member count makes size() immediate. Both must then be kept correct by every function that changes the list.

5. A list iterator (script 16.2)

Our list is a container, but it can't yet be used with the iterator loop of lesson 11. For that we need an iterator class with operator*, operator++ and operator!=, and list functions begin() and end() (p. 193). The iterator belongs to our list, so it is defined inside it, as an inner class: its full name is our_list::iterator (p. 193–194).

Its state is one node pointer (Example 16.7):

  • constructor: iterator(lnode* n) : node(n) {};
  • ++: node = node->next; return *this; (with assert(node != nullptr) first);
  • *: return node->value;, as int&, so *it = 5 changes the element;
  • !=: return node != other.node;: two iterators are equal if they point to the same node;
  • in the list: begin() is iterator(head), end() is iterator(nullptr), the "place behind the last node".

Now the secret of lesson 11 is out: an iterator is a small object wrapping a pointer, and *it and ++it are member functions that follow it. With these parts, our list works with the range-based for (p. 196). Coding task 4 builds it.

Worked example 3: where does end() point?

  1. For the list head → 3 → 9, how many times does the body of for (auto it = l.begin(); it != l.end(); ++it) run, and which nodes does it.node visit?
    Answer

    Twice: node 3, node 9, then nullptr, which equals end(): stop. The iterator loop is exactly the walk for (lnode* n = head; n != nullptr; n = n->next) in disguise.

  2. For the empty list?
    Answer

    begin() is iterator(head) = iterator(nullptr) = end(): the body never runs, as for every empty container.

Coding task 1: a train of any length (script Example 15.18)

Read n ≥ 1 and then n wagon numbers. Build the train in that order, every wagon made with new, then walk it from the first wagon and print the numbers, separated by spaces.

You'll need these

new wagon(id) (section 3), the arrow -> (section 2) and the walk of section 4.

What the contract forces (before any idea)
  • Given: n ≥ 1 numbers, in order.
  • Must hold at the end: a chain first → … → last, in input order, the last hook nullptr; output in the same order.
  • The gap to fill: appending at the back without walking the chain each time.

Try it yourself: write the building loop and the printing loop, then press Check.

int main() {

  std::cin >> n;
  assert(n >= 1);
  int id;
  std::cin >> id;

  wagon* last = first;
  // todo: read the other n - 1 numbers and append a wagon for each
  // todo: walk from first and print every id
  std::cout << "\n";
  return 0;

  1. What does last point to before and after each round?
    My answer

    Before: the current last wagon. In the round, a new wagon is clipped to it (last->next = …) and then last moves on to the new one. So the statement "last points to the last wagon" holds after every round: an invariant.

  2. In which order must the two assignments come?
    My answer

    First last->next = w;, then last = w;. The other way round, last would already be w, and w would be clipped to itself; the old last wagon would never get its hook set.

  3. How does the printing loop know when to stop?
    My answer

    The last wagon's hook is still nullptr from the constructor. The walk stops when w becomes nullptr.

Coding task 2: push_back and size (script Examples 16.2 and 16.3, p. 193)

Complete our_list: push_back(e) appends e at the end, also when the list is empty, and size() returns the number of elements. The program reads m numbers, appends each, then prints the list and its size.

You'll need these

The walk and the buggy push_back of section 4, and the list method, question 4.

What the contract forces (before any idea)
  • Given: a list in any state, including empty.
  • Must hold at the end: push_back: e is the new last element, the others unchanged; size: the count, list unchanged (const).
  • The gap to fill: which pointer changes when the list is empty, and which when it isn't?

#include <iostream>

struct lnode {

class our_list {

  void print() const {
    for (lnode* n = head; n != nullptr; n = n->next)
      std::cout << n->value << " ";
  }

  // POST: e has been added at the front
  void push_front(int e) {
    head = new lnode(e, head);
  }

  // POST: e has been added at the end
  void push_back(int e) {
    // todo
  }

  // POST: returns the number of elements
  int size() const {
    // todo
    return 0;
  }
};

int main() {
  our_list l;
  int m;
  std::cin >> m;
  for (int i = 0; i < m; ++i) {
    int x;
    std::cin >> x;
    l.push_back(x);

  1. Which pointer gets the new node, in each case?
    My answer

    Empty list: head itself (there is no last node). Otherwise: next of the last node. Two different pointers, so two cases.

  2. How do you find the last node?
    My answer

    Walk while n->next != nullptr: the loop stops on the last node, not behind it. With n != nullptr it would end on nullptr, and you couldn't clip anything to it.

  3. Why may size() be const, but not push_back?
    My answer

    size only reads the pointers; push_back changes head or a node's next. (Strictly, a const function may change the nodes, since head stays the same pointer; but the promise "the list doesn't change" is what const should express.)

  // POST: e has been added at the end
  void push_back(int e) {
    if (head == nullptr) {         // Case 1: empty list
      head = new lnode(e, nullptr);
    } else {                       // Case 2: non-empty list
      lnode* n = head;
      for (; n->next != nullptr; n = n->next);
      n->next = new lnode(e, nullptr);
    }
  }

  // POST: returns the number of elements
  int size() const {
    int c = 0;
    for (lnode* n = head; n != nullptr; n = n->next)
      ++c;
    return c;
  }
};

int main() {
  our_list l;
  int m;
  std::cin >> m;
  for (int i = 0; i < m; ++i) {
    int x;
    std::cin >> x;
    l.push_back(x);
  }
  l.print();
  std::cout << "size " << l.size() << "\n";
  return 0;
}

  5. Tests.
    My answer

    The script's list 1 5 6; no numbers (size 0, and nothing may crash); one number (only case 1 runs); a longer list (order kept); zeros (values don't matter to the pointers).

  6. The first push_back of every list takes case 1. Which test would have caught the buggy version?
    My answer

    Every test with m ≥ 1: the very first push_back is on an empty list and crashes. That is why the script calls the empty list the first case to think of.

Patterns used: empty case first walk the nodes accumulator

How to write this under exam pressure
  1. Before every n->, ask: can n be nullptr here?
  2. Empty list: head changes. Otherwise: some next changes.
  3. Stop on the last node with n->next != nullptr; walk past all nodes with n != nullptr.

In short: "empty first, then walk".

Coding task 3: a sorted list with a sentinel (IFMP exam January 2017, task 8, 8 points)

A sorted list stores characters in increasing ASCII order. It always starts with an artificial first node holding ':', a sentinel, so that inserting needs no special case. insert(k) adds k and keeps the order; print() outputs the elements in order, without the sentinel. Inserting the characters of "ifmp16" one by one gives the output 16fimp. (The exam writes 0 for the null pointer; that is older C++ and means nullptr.)

You'll need these

The walk (section 4), push_front's one line new lnode(e, …), and p->next->key read left to right (section 2).

What the contract forces (before any idea)
  • Given: a sorted list, always with the sentinel in front.
  • Must hold at the end: k is in the list and the list is still sorted; print shows everything after the sentinel.
  • The gap to fill: to insert, you must stop at the node before the place, because that node's next changes.

    My answer

  2. Why must p->next != 0 come first in the condition?

Coding task 4: an iterator for our list (script Examples 16.7 to 16.13)

Complete the inner class our_list::iterator and the functions begin() and end(). The program then adds k to every element with an iterator loop and prints the list with a range-based for; both only work once your iterator does.

You'll need these

Section 5, the operator functions of lesson 9 (here as member functions), and return *this; for ++.

What the contract forces (before any idea)
  • Given: a list of nodes; an iterator holds one node pointer.
  • Must hold at the end: begin() on the first node, end() "behind the last" (nullptr); ++ moves to the next node; * gives a reference to the value; != compares positions.

  1. Why does operator* return int&, not int?
    My answer

    *it += k must change the value inside the node. With int, it would change a copy (lesson 9, "return a reference").

  2. Why may operator* be const, although it allows changing the element?
    My answer

    const protects the iterator: its member node isn't changed. The node it points to is not part of the iterator. (The same as int* const p: the pointer is fixed, the int is not.)

  3. Why can end() simply be iterator(nullptr)?
    My answer

    Walking with ++ from the last node gives node = last->next = nullptr. So "behind the last element" is exactly the null pointer, and comparing with it is the walk's stop test.

Worked example 4: dot or arrow?

With wagon w = wagon(1); wagon* p = &w;, which expressions are correct for w's id?

  1. w.id, p.id, p->id, (*p).id, *p.id?
    Answer

    Correct: w.id (an object: dot), p->id and (*p).id (a pointer: arrow, or dereference then dot). Wrong: p.id (a pointer has no members) and *p.id (means *(p.id)).

  2. In the list code, why is it always n->next and never n.next?
    Answer

    n is an lnode*. In list code you almost never hold a node itself, only pointers to nodes; so it is arrows everywhere.

Worked example 5: operator[] with an assertion (script p. 190)

The script suggests, as an exercise, changing operator[] so that an assertion fails when i is too large.

  1. Where does the assertion go?
    Answer

    Inside the loop, before every step: for (int j = 0; j < i; ++j) { assert(n != nullptr); n = n->next; }, and once more after the loop, assert(n != nullptr);, before return n->value;. The second one catches i == size, which the first doesn't.

  2. Why is l[i] in a loop over all i a bad idea for a list?
    Answer

    Each l[i] walks i steps from head. For n elements that is 0 + 1 + … + (n − 1), about n²/2 steps, against n for the walk or the iterator. That is the "no efficient random access" of p. 188.

Exercise 5 (true or false) · 4 points

  1. An object created with new inside a function is released when the function ends.
  2. head = new lnode(e, head); is correct also for an empty list.
  3. A linked list offers fast access to its i-th element.
  4. p->value is the same as (*p).value.
Solution

Frame: sections 2 to 4, one rule each.

1. False: it lives until it is deleted; only the pointer variable disappears. 2. True: the new node's next becomes nullptr. 3. False: you walk i steps from head. 4. True: that is what the arrow means.

Summary: what to keep from lesson 12

  • Pointers: T* p = &x; holds the address of x; *p is x; p->m is (*p).m; nullptr points nowhere and must never be dereferenced. Unlike a reference, a pointer can be redirected.
  • Const: read right to left. int const* p: the int is read-only. int* const p: the pointer is fixed.
  • new: new T(...) makes an object at runtime and returns its address; it lives until deleted.
  • Linked list: nodes with value and next; the list holds head. Walk: for (lnode* n = head; n != nullptr; n = n->next). push_front: head = new lnode(e, head);. push_back: empty case first. Sentinel: a dummy first node removes special cases.
  • Iterator: an inner class holding a node pointer; ++ follows next, * gives node->value by reference, != compares nodes; begin() is head, end() is nullptr.

For wonder: the billion-dollar mistake (optional, 5 min)

The null pointer was invented in 1965 by Tony Hoare, for the language ALGOL W, "simply because it was so easy to implement". In 2009 he called it his "billion-dollar mistake": a null pointer dereferenced by accident has crashed countless programs since, and caused untold security holes. C++ kept it, and gave it the clearer name nullptr in 2011 (before, people wrote 0 or NULL, as in the 2017 exam). Newer languages try to make the mistake impossible: in Rust or Swift, a value that might be missing has its own type, and the compiler refuses to let you use it before you have checked. In C++, the check is your job, which is why the list method asks before every n->: can n be nullptr here?
